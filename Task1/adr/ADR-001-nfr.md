# ADR-001: Нефункциональные требования (НФТ) целевой платформы GoFuture

- **Автор:** Дмитрий Ренев
- **Статус:** На согласовании
- **Согласующие:** Дмитрий Бардин
- **Этап плана декомпозиции:** 1 – проработка нефункциональных требований
- **Дата:** 2026-10-12
- **Связанные артефакты:** [c2-to-be.puml](../diagrams/c2-to-be.puml), [ADR-002-service-map-and-c2](../adr/ADR-002-service-map-and-c2.md)

## Контекст

"GoFuture" – платформа агрегации такси (пассажирское, водительское приложения, корпоративный веб-портал) на монолите 
Django + PostgreSQL RDS. Компания масштабируется на Юго-Восточную Азию и Южную Америку, но монолит не выдерживает роста:
- пиковые нагрузки **более 100 тыс. активных поездок** вызывают каскадные отказы;
- **MTTR > 4 часов**, доступность критичных сценариев нестабильна;
- время выхода новых функций **≥ 6 месяцев**;
- масштабирование вертикальное и **ручное по алертам** (без автоскейла);
- сборка монолита **> 30 минут**.

Целевое состояние (через 12 месяцев): микросервисная архитектура с независимыми доменами, **500 тыс. конкурентных поездок**, 
**99,95 % доступности критичных сервисов**, **горизонтальный автоскейл в ≥ 3 регионах**, **time-to-market новых функций ≤ 2 недель**, соответствие локальным регуляторным требованиям.

НФТ задают измеримые границы, которым должны удовлетворять карта сервисов (ADR-002), очерёдность выделения (ADR-003), 
механизмы обратной совместимости (ADR-004) и план миграции (ADR-005). Это "рамка качества", относительно которой проверяется 
каждый последующий архитектурный шаг.

## Требования

1. Сформулировать НФТ по категориям: производительность, масштабируемость, доступность, отказоустойчивость (RTO/RPO), задержка, безопасность, комплаенс/резидентность, наблюдаемость, стоимость (FinOps), сопровождаемость/DORA, совместимость API, консистентность данных.
2. Для каждого требования задать **числовую цель**.
3. Отделить требования, критичные для выделения сервисов, от "справочных".
4. Зафиксировать допущения и открытые вопросы.

## Решение

| NFR-P-03 | Производительность | Подбор водителя (matching) | p95 ≤ 1 с |

### Пояснения по ключевым требованиям

**NFR-A-01 (доступность).** 99,95 % – базовое требование контекста для критичных сервисов; так же ставится цель 99,99 % на 
регион через геораспределение. Для внутреннего бюджета ошибок принимаем худшее из значений в зависимости от региона 
развёртывания.

**NFR-P-01…P-04 (производительность).** Нагрузка 500 тыс. конкурентных поездок недостижима на текущем монолите; 
требования задают цель для карты сервисов и обосновывают выделение "горячих" доменов для независимого 
масштабирования.

**NFR-A-02 (изоляция сбоев).** Ограничение каскадных отказов – прямое следствие текущей проблемы; требует на уровне каждого 
межсервисного вызова применять таймауты, retry с backoff, circuit breaker и bulkhead.

**NFR-P-06, NFR-A-06, NFR-O-04 (брокер событий).** Целевая нагрузка и event-driven модель требуют брокера класса log-based 
(Apache Kafka) вместо RabbitMQ: пропускная способность, retention/replay и at-least-once с идемпотентностью. 
RabbitMQ не покрывает требования по throughput и replay.

**NFR-C-01/C-02 (комплаенс).** Резидентность данных напрямую влияет на модель данных: сервисы, работающие с PII, должны уметь 
разворачиваться per-region с изоляцией PII.

**NFR-D-01 и NFR-COMPAT-01/02.** Распределённые транзакции заменяются сагами и идемпотентностью; совместимость API и схем событий 
– обязательное условие near-zero-downtime миграции.

### Критичные для декомпозиции требования

- **Для выбора границ сервисов:** NFR-SC-02, NFR-A-02, NFR-C-01, NFR-D-01 (изоляция, независимое масштабирование, резиденция данных, согласованность).
- **Для плана миграции:** NFR-COMPAT-01/02, NFR-A-04 (совместимость, RTO/RPO).
- **Для механизмов совместимости:** NFR-COMPAT-01/02, NFR-O-02 (версионирование, трассировка).
- **Для выбора брокера событий:** NFR-P-06, NFR-A-06, NFR-O-04 (пропускная способность, доставка/retention, наблюдаемость).

## Альтернативы

1. **Использовать "мягкие" НФТ без чисел.** Гибко, но неизмеримо и не даёт критериев приёмки.
2. **Взять отраслевые бенчмарки (например, только SLA облака).** Не отражает специфику маркетплейса такси (matching-latency, hot zones).

## Компромиссы и риски

- **p95/p99 задержки** зависят от географии клиента; без регионального развёртывания цели достижимы только для "ближнего" региона.
- **Стоимость (NFR-COST-01).** Декомпозиция временно повышает издержки (двойная инфраструктура, dual-write); −40 % достижимо к концу года, не на переходном периоде.
- **Комплаенс по регионам** требует юридической валидации; архитектура даёт техническую возможность изоляции, но не заменяет compliance-оценку.
- **NFR-M-02 (сборка ≤ 15 мин).** Достижимо только после распила CI на сервисы; до этого монолит остаётся узким местом.

## Допущения

- Пиковая нагрузка 500 тыс. конкурентных поездок – глобальная (сумма по регионам), распределяемая геомаршрутизацией.
- "Критичные сервисы" для SLA: Booking, Driver, Payments, Geography (допущение, уточняется у бизнеса).
- Целевой облачный провайдер сохраняется (Yandex Cloud) в рамках эволюции стека.
