# ADR-005: План миграции данных для каждого сервиса

- **Автор:** Дмитрий Ренев

## Контекст

Сейчас **все домены используют одну БД PostgreSQL RDS**. Целевая модель – **database-per-service** (ADR-002).
Объём данных большой (таблицы поездок, платежей, устройств, событий – миллионы/миллиарды записей, поэтому 
"останови и перенеси" недопустимо: нужно минимизировать время простоя (NFR-A-04) и обеспечить совместимость (ADR-004).

Переход – инкрементальный, по волнам (ADR-003), для каждого сервиса отдельно.

## Требования

1. Определить стратегию миграции данных для каждого сервиса.
2. Обеспечить минимизацию времени простоя (цель: near-zero; допустимое окно – только для исключительных случаев).
3. Учесть большой объём: миграция без блокировки, с throttling и без влияния на продуктивный трафик.
4. Обеспечить целостность и проверяемость (reconciliation, контрольные суммы, отчёты расхождений).
5. Предусмотреть репликацию данных в регионы (резидентность, NFR-C-01).
6. Задать критерии cutover и план отката.

## Решение

### Базовая стратегия (для всех сервисов): Strangler Fig + Dual-write + CDC + Backfill

1. **Аудит схемы БД.** Полный аудит схемы БД: какие таблицы принадлежат какому домену, кто пишет/читает, зависимости, объёмы, PII.
2. **Разделение владения.** Определить целевую БД/схему сервиса (database-per-service) и правила маппинга.
3. **CDC (Debezium → Kafka).** Включить захват изменений из WAL монолита и публикацию в брокер событий (Kafka); сервис применяет поток к своей БД в реальном времени.
4. **Backfill (историческая загрузка).** Пакетно перенести исторические данные чанками (например, по диапазонам PK/дат), с throttling, в период низкой нагрузки; прогресс и лаг контролируются.
5. **Dual-write (Transactional Outbox).** На время перехода записи идут и в монолит, и в сервис через outbox, чтобы не терять события и не рассинхронизировать данные (см. ADR-004).
6. **Валидация и reconciliation.** Сверка: количество строк, контрольные суммы по ключевым полям, бизнес-инварианты, отчёт расхождений; автоматический "repair" при расхождениях.
7. **Shadow reads.** Сервис отвечает на копию трафика; сравнение ответов с монолитом (diff), устранение расхождений.
8. **Cutover.** Переключение чтения/записи на сервис с помощью feature flag/шлюза: canary → 10 % → 50 % → 100 %.
9. **Стабилизация и вывод.** После периода стабильности: отключение dual-write, удаление фасада, архивация/удаление "осиротевших" таблиц в монолите.

### План по сервисам

Оценка объёма – допущения (уточняются при при аудите схемы БД).

| Волна | Сервис | Источники данных                       | Хранилище To-Be | Стратегия миграции | Особенности | Окно простоя |
|:----:|--------|----------------------------------------|-----------------|--------------------|-------------|:----:|
| 1 | **Notification** | devices, templates, notification_log   | PostgreSQL | CDC + backfill → dual-write → cutover | Async, низкая критичность; можно переносить потоком | 0 (near-zero) |
| 2 | **Analytics** | events, aggregates                     | ClickHouse (+ поток) | Поток событий + разовая загрузка истории | Read-only профиль; бэкфилл больших объёмов throttled | 0 |
| 3 | **Fraud** | fraud_rules, risk_scores               | PostgreSQL | CDC + backfill → dual-write | Async-потребитель; нужен доступ к событиям Payments/Booking | 0 |
| 4 | **Geography** | drivers (geo), zones, geo_index        | PostgreSQL + Elasticsearch | Backfill геоданных + перестройка индекса ES; CDC для изменений | Геоиндекс перестраивается в фоне; переключение поиска через шлюз | 0 |
| 5 | **Pricing** | pricing_rules, quotes, surge-состояние | PostgreSQL + Redis | Backfill правил + CDC; кеш прогревается до cutover | Latency-критично → прогрев кеша обязателен | 0 |
| 6 | **Payments** | payments, transactions, refunds        | PostgreSQL | CDC + backfill → dual-write → cutover; **регуляторный аудит** | Финансовый риск, PCI DSS, обязательная reconciliation; возможно короткое окно | Возможен плановый (напр. ≤ 5 мин) |
| 7 | **Payouts** | payouts, balances                      | PostgreSQL | CDC + backfill → dual-write; сверка балансов | Работа с деньгами водителей; строгая сверка балансов до/после | Возможен плановый (≤ 5 мин) |
| 8 | **Driver** | drivers, shifts, earnings              | PostgreSQL | CDC + backfill → dual-write → cutover | Много потребителей (Booking, Geography, Payouts) – координировать | 0 |
| 9 | **Booking** | bookings, trip_state                   | PostgreSQL | CDC + backfill → dual-write → cutover | Ядро; вынос последним, завершает вывод монолита | 0 |

### Работа с большим объёмом данных

- **Чанкованный backfill**: разбивка по диапазонам первичных ключей/дат; параллельные воркеры с ограничением RPS; сохранение контрольных точек (resume).
- **Throttling и окна нагрузки**: миграция в часы минимума; лимит на репликацию, чтобы не деградировать продуктив (NFR-P-02).
- **Инкрементальный "догон"**: CDC непрерывно доносит изменения, пока идёт backfill → финальная дельта минимальна.
- **Отдельная реплика для чтения** под backfill, чтобы не нагружать primary.
- **Идемпотентная загрузка**: повторная обработка чанка не создаёт дублей (upsert по ключу).

### Критерии готовности к cutover

- Лаг CDC ниже заданного порога (например, < 5 с) стабильно в течение N часов.
- Reconciliation: расхождения по ключевым таблицам = 0 (или в пределах допустимого, задокументированного порога).
- Shadow-тесты: diff ответов < порога.
- Прогреты кеши (Redis) и индексы (ES) для geography/pricing.
- Алерты, метрики и трейсы сервиса настроены (NFR-O-01/NFR-O-02).
- Runbook откатов и ответственные дежурные назначены.

### План отката

- Маршрут трафика в шлюзе/фасаде переключается флагом → мгновенный возврат на монолит.
- Dual-write сохраняется до подтверждённой стабильности → данные согласованы при откате.
- Backfill можно перезапускать с контрольной точки.
- "Вспомогательные" хранилища (ES, Redis, ClickHouse) восстанавливаются из источника.

### Данные, чувствительные к регуляторике

- **Резидентность PII** (NFR-C-01/C-02): данные пассажиров/водителей по региону хранятся в регионе присутствия; миграция учитывает регионализацию.
- **Retention и аудит** (NFR-C-03): финансовые транзакции и audit-log переносятся с сохранением неизменяемости и сроков хранения.

## Альтернативы

1. **Big-bang миграция в одно окно.** Проста, но неприемлема по объёму и NFR-A-04.
2. **Логическая репликация без backfill (только новые данные).** Не покрывает историю. 
3. **Backfill без CDC.** Не покрывает изменения во время загрузки → рассинхронизация.
4. **Снапшот + переключение.** Возможен для небольших изолированных хранилищ (например, ES-индекс), но не как общая стратегия.
5. **Только dual-write (без CDC).** Не ловит изменения в обход API (admin, прямые SQL).

## Компромиссы и риски

- **Dual-write создаёт двойную нагрузку и повышает сложность**; требует outbox, идемпотентности и reconciliation.
- **Большой backfill** может влиять на продуктивную БД → обязателен throttling и реплика для чтения.
- **CDC-лаг** и расхождения – основной риск; митигация: мониторинг лага, пороги, автоматический repair.
- **Финансовые сервисы (Payments/Payouts)** – максимальный риск; приоритет корректности над zero-downtime (допустимо короткое плановое окно).
- **Вывод монолита** (удаление таблиц) необратим – выполняется только после долгого периода стабилизации и архивации.
- **Стоимость** двойной инфраструктуры на переходном периоде (NFR-COST-01).
- **Регионализация данных** усложняет миграцию.

## Допущения

- Доступна логическая репликация PostgreSQL (RDS) и механизм CDC (Debezium).
- Используется брокер событий Apache Kafka для потока CDC-изменений.
- Для каждого сервиса есть возможность выделить ключ/диапазон для чанкованного backfill.
- Объёмы уточняются на этапе аудита схемы БД; приведённые стратегии не зависят от точного размера.
