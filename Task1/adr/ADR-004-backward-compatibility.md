## Контекст

Декомпозиция идёт инкрементально (волны, ADR-003) и требует **near-zero downtime** (NFR-A-04, NFR-COMPAT-01). В переходный период одновременно живут три "мира":

1. **Монолит** (не перенесённые домены и strangler-фасад).
2. **Новые сервисы** (уже выделенные домены).
3. **Клиенты** (мобильные приложения iOS/Android/Huawei, веб-портал), которые **нельзя обновить мгновенно** – часть пользователей остаётся на старых версиях недели и месяцы.

Дополнительно: домены обмениваются и синхронно (REST), и асинхронно (события). Значит, нужна совместимость и на уровне **API**, и на уровне **схем событий**.

## Требования

1. Клиенты (старые и новые версии) должны работать без изменений на протяжении всей миграции.
2. Новый сервис должен переиспользовать/адаптировать существующую модель, не ломая потребителей.
3. Обеспечить минимизацию времени простоя при переключении трафика между монолитом и сервисом.
4. Поддержать одновременную работу монолита и сервиса (в т.ч. на общих данных) без рассинхронизации.
5. Обеспечить совместимую эволюцию схем событий.
6. Дать механизм безопасного отката (rollback) на любом шаге.

## Решение

### Комплекс механизмов

| № | Механизм                                    | Назначение | Реализация |
|---|---------------------------------------------|------------|------------|
| 1 | **API Gateway / BFF**                       | Единая точка входа, маршрутизация между монолитом и сервисами, аутентификация, rate limiting, версионирование | Шлюз перед монолитом и сервисами; BFF (passenger/driver/portal) при различии контрактов клиентов |
| 2 | **Strangler facade в монолите**             | Перехват вызовов к "уже выделенному" домену и проксирование в новый сервис | Модуль-фасад внутри Django; включает/выключает маршрут (feature flag) |
| 3 | **API Versioning**                          | Обратная совместимость публичных API | URI-версии (`/v1`, `/v2`) + заголовки `Deprecation`, `Sunset`; поддержка **N-1** версии, deprecation ≥ 2 релиза |
| 4 | **Anti-Corruption Layer (ACL)**             | Изоляция доменной модели сервиса от легаси-модели монолита | Адаптеры маппинга DTO ↔ домен; не допускают "протечку" легаси-модели в новый домен |
| 5 | **Dual-write + Transactional Outbox**       | Параллельная запись в монолит и сервис в переходный период без потери событий | Запись в основную БД + outbox-таблица в одной транзакции; воркер публикует в брокер событий (Kafka) |
| 6 | **CDC (Debezium/логическая репликация)**    | Синхронизация изменения данных из монолита в сервис (и обратно при необходимости) | Чтение WAL PostgreSQL → запись в целевую БД / публикация в брокер |
| 7 | **Contract testing (Pact)**                 | Гарантия, что новый сервис соблюдает контракт потребителей | Consumer-driven контракты в CI; блокировка релиза при breaking change |
| 8 | **Feature flags + Canary + Shadow traffic** | Безопасное переключение и проверка на реальном трафике | Флаги on/off по региону/тенанту; canary 1→10→50→100 %; shadow-запросы (сравнение ответов без влияния) |
| 9 | **Совместимая эволюция схем событий**       | Совместимость контрактов событий между сервисами | Только backward-compatible изменения схем |
| 10 | **Idempotency keys + дедупликация**         | Защита от дублей при ретраях/dual-write | Идемпотентные ключи на операциях записи; уникальные индексы |
| 11 | **Deprecation policy**                      | Управляемое выведение старых контрактов | Публикация сроков, телеметрия использования версии, отключение после истечения |


### Сценарии совместимости по типам изменений

| Тип изменения | Подход |
|---------------|--------|
| Новое поле в API-ответе | Добавляется опционально → backward-compatible, версия не меняется |
| Удаление/переименование поля | Новая версия (`/v2`), старая поддерживается N-1 |
| Изменение семантики | Новая версия + миграционный гайд + deprecation-срок |
| Новое поле в событии (обязательное) | Только через новую версию топика/схемы; backward-compatible обязательна |
| Вынос домена в сервис | Шлюз + фасад переключают маршрут; клиенты не меняются |
| Изменение хранилища | Dual-write + CDC + backfill (ADR-005), без изменения API |

### Порядок применения при выносе сервиса (для каждой волны)

1. Поднять сервис "теневым" (не в трафике), подключить ACL и хранилище.
2. Включить **dual-write / CDC** – сервис и монолит получают оба потока.
3. Включить **shadow traffic** и сравнить ответы (diff), исправить расхождения.
4. Включить **canary** для малой доли трафика через шлюз/фасад.
5. Постепенно увеличить до 100 %; старый путь остаётся в режиме "горячего резерва".
6. После периода стабилизации отключить dual-write и удалить фасад (отдельный шаг, ADR-005).

### Обеспечение отката

- Маршрутизация в шлюзе/фасаде – переключатель (flag) → мгновенный откат трафика на монолит без релиза клиентов.
- Dual-write не отключается до подтверждённой стабильности → данные не рассинхронизируются при откате.
- Версии API не удаляются до истечения deprecation-окна.

## Альтернативы

1. **Принудительное обновление всех клиентов до миграции.** Невероятно дорого/невозможно для мобильных приложений (Huawei/старые версии).
2. **Big-bang переключение с окном простоя.** Проще, но нарушает NFR-A-04 и NFR-COMPAT-01.
3. **Только CDC без dual-write.** Дешевле по записи, но увеличивает лаг и риск рассинхронизации в момент cutover
4. **Только dual-write без CDC.** Не покрывает изменения, сделанные в обход (например, прямые SQL-операции, admin-панель).
5. **GraphQL-фасад как универсальный ACL.** Гибко для клиентов, но добавляет сложность и не решает совместимость событий.

## Компромиссы и риски

- **Dual-write повышает задержку и сложность**; требует идемпотентности и обработки частичных сбоев. Митигация: outbox + ретраи + reconciliation.
- **Шлюз – единая точка отказа.** Требует HA-развёртывания и мониторинга (NFR-A-02).
- **Поддержка N-1 версий** увеличивает объём сопровождаемого кода.
- **Shadow traffic** удваивает нагрузку на сервис в тестовом режиме – ограничивается долей трафика.
- **CDC** чувствителен к изменениям схемы и объёму; требует контроля лага.
- **Версионирование API** замедляет скорость внедрения breaking changes (обратная сторона стабильности).
- **Совместимость схем событий** требует дисциплины контрактов. Нарушение backward-compatible эволюции ломает потребителей.

## Допущения

- Публичные контракты для мобильных клиентов достаточно стабильны, чтобы жить с N-1 версиями.
- В качестве брокера событий используется **Apache Kafka**; RabbitMQ выводится (ADR-006).
- Команды готовы писать consumer-driven контракты (NFR-M-04).
