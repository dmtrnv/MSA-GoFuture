## Контекст

В As-Is RabbitMQ используется одновременно как:
- **task queue** для Celery (асинхронные задачи: уведомления, выплаты, аналитика);
- **брокер async-интеграций** между доменами монолита (протокол AMQP).

Целевые требования (ADR-001) задают нагрузку **500 тыс. конкурентных поездок**, event-driven обработку в реальном времени и задел под **геораспределение**. 

RabbitMQ на такую роль не рассчитан:
- ограниченная пропускная способность кластера, при этом quorum-очереди реплицируются на все узлы (write amplification) и плохо масштабируются горизонтально для одной очереди;
- нет нативного **лога с retention/replay** – события потребляются и исчезают, нет переигрывания для восстановления потребителей, event sourcing и аналитики;
- менее удобен для высокочастотных fan-out потоков и геораспределённой репликации.

Apache Kafka закрывает эти требования: партиционирование, retention, replay, упорядоченность в партиции, consumer groups, репликация между регионами – то есть именно то, что нужно для целевой нагрузкой и геораспределения.

Предлагается перевести на Kafka все типы интеграций, где сейчас используется RabbitMQ.

## Требования

1. Единый **event-driven backbone** для всех async-интеграций (доменные события + фоновые задачи).
2. Пропускная способность под 500 тыс. конкурентных поездок и высокочастотные потоки событий.
3. Гарантии доставки **at-least-once** + идемпотентное потребление; retention и возможность replay.
4. Надёжная **публикация** доменных событий на стороне продюсера: **Transactional Outbox** (атомарно с записью в БД), без потери и без фантомных событий.
5. Задел под **партиционирование по регионам** и георепликацию.
6. **Полный вывод RabbitMQ** и отказ от идиомы Celery-задач в пользу Kafka-consumer'ов.
7. Минимизация времени простоя; переход **по доменам**, без параллельного dual-run.
8. Использование управляемого сервиса в текущем облаке (Yandex Cloud).

## Решение

### Выбор платформы

- **Apache Kafka**, развёрнутый как **Yandex Managed Service for Apache Kafka**.
- Один Kafka-кластер как минимум на переходном этапе, с заделом на георепликацию
- Kafka работает в режиме транспорта: **топики по доменам**, партиционирование с учётом региона.
- **Schema Registry** и режим backward-compatible эволюции схем – базовый принцип.

### Замена типов интеграций

| Что было (RabbitMQ) | Что становится (Kafka) |
|---------------------|------------------------|
| Async-интеграции между доменами (AMQP) | Доменные события в Kafka-топиках |
| Celery task queue (уведомления, выплаты, аналитика) | Kafka-consumer-сервисы / Kafka Streams (consumer groups) |
| Celery Beat (периодические задачи) | Планировщик на стороне сервисов / Kafka-триггеры |

### Гарантии и механики

- Доставка **at-least-once**; потребители **идемпотентны** (ключи события, upsert).
- Неуспешная обработка – через **retry-топики и dead-letter topic**.
- **Retention** событий (достаточный для replay и восстановления потребителей) и переигрывание при необходимости.
- Мониторинг **consumer lag**, throughput, rebalance (увязка с NFR-O-01).
- Принцип эволюции схем – только backward-compatible (см. ADR-004).

## План перехода RabbitMQ → Kafka (по доменам, без dual-run)

Стратегия: интеграции каждого домена переводятся **в рамках его волны выделения** (ADR-003). RabbitMQ и Kafka параллельно на постоянной основе **не работают**; допускается лишь короткое окно переключения на конкретный домен.

### Этап 0 – Подготовка Kafka (Волна 0, месяцы 1–2)

1. Развернуть **Yandex Managed Kafka**, настроить доступ из монолита.
2. Базовая observability: consumer lag, throughput, ошибки, алерты.
3. Задать retention и политику (retry-топики, dead-letter).
4. Зафиксировать клиентские библиотеки и базовый Schema Registry.
5. Создать базовые доменные топики.
6. Пилотный перевод **одного** низкорискового потока (уведомления) для валидации процесса.

### Этап 1..N – Перевод по доменам (Волны 1–9)

Для каждого домена при его выделении:

1. Настроить продюсеров и консьюмеров домена на Kafka; включить **Transactional Outbox** (outbox-таблица + relay) для домена.
2. **Переключить продюсера**: прекратить публикацию в RabbitMQ для этого домена и начать публиковать в Kafka **через outbox**.
3. **Переключить консьюмеров** и **дождаться опустошения** backlog RabbitMQ по домену до нуля (in-flight задачи не теряются).
4. Задачи Celery для домена заменяются Kafka-consumer'ами; дождаться пустых очередей Celery перед выключением.
5. Проверить lag, консистентность и replay; включить штатный режим.
6. Удалить очереди/обменники RabbitMQ и Celery-таски этого домена.

### Этап Финал – Вывод RabbitMQ (к концу года)

После перевода последнего домена (Волна 9, Booking) – вывод RabbitMQ и Celery Beat.

### Особый случай: финансовые домены (Payments, Payouts)

Из-за регуляторного и финансового риска для этих доменов рекомендуется (как исключение) **кратковременный параллельный dual-publish** на время окна переключения – чтобы иметь возможность отката без потери сообщений. Это отклонение от общей стратегии "без dual-run" согласуется отдельно.

## Альтернативы

1. **Оставить RabbitMQ.** Не выдерживает целевую нагрузку, нет replay/retention, плохое горизонтальное масштабирование очереди.
2. **Гибрид: RabbitMQ для task-queue + Kafka для событий.** Возможен, но усложняет эксплуатацию (два брокера).
3. **Celery поверх Kafka-transport.** Нестандартно, ограниченная поддержка, не даёт преимуществ Kafka.
4. **Self-hosted Kafka (Strimzi/K8s).** Больше контроля, но выше операционная нагрузка.
5. **Переход через длительный dual-run RabbitMQ+Kafka.** Безопаснее (мгновенный откат), но дороже и сложнее.

## Компромиссы и риски

- **Отказ от dual-run** – нет простого мгновенного возврата на RabbitMQ; при ошибке возможна потеря/задержка сообщений. Митигация: короткие окна на домен, canary-потребители, идемпотентность, **retention и replay из Kafka** для восстановления, runbook, для финансовых доменов – исключение с dual-publish.
- **Celery→Kafka consumers** меняет модель фоновых задач: нет готовых приоритетов/отложенных задач "из коробки" – реализуются через топики/ретраи.
- **Transactional Outbox вводит дополнительную запись** в каждой транзакции и асинхронный лаг relay (eventual consistency публикации). Митигация: компактный конверт события, retention/партиционирование outbox-таблицы, метрики publish-lag; для sync-сценариев критичного пути остаётся REST/gRPC.
- **Эксплуатационная сложность Kafka** выше RabbitMQ; managed-сервис снижает, но вводит зависимость от провайдера и его квот.
- **Латентность** для мелких командных задач может быть выше, чем у RabbitMQ; для latency-критичных сценариев остаются REST/gRPC.
- **Идемпотентность обязательна** (at-least-once) – рост требований к обработке дублей.
- **Стоимость** managed Kafka и трафика между регионами (учитывать в FinOps, NFR-COST-01).

## Допущения

- Yandex Managed Kafka доступен в целевых регионах и покрывает квоты по throughput/retention.
