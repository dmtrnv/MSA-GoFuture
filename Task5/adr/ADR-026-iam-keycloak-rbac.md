# ADR-026: IAM-система (Keycloak), SSO/OIDC и ролевой доступ (RBAC+ABAC)

- **Автор:** Дмитрий Ренев
- **Статус:** На согласовании
- **Согласующие:** Дмитрий Бардин
- **Дата:** 2026-10-18
- **Связанные артефакты:** [ADR-001-nfr.md](../../Task1/adr/ADR-001-nfr.md), [ADR-013-deployment-regions.md](../../Task3/adr/ADR-013-deployment-regions.md), [ADR-017-compliance.md](../../Task3/adr/ADR-017-compliance.md), [ADR-018-security-landscape.md](../../Task3/adr/ADR-018-security-landscape.md), [ADR-024-data-residency.md](../../Task4/adr/ADR-024-data-residency.md), [ADR-025-tenant-isolation.md](ADR-025-tenant-isolation.md), [ADR-027-partner-onboarding.md](ADR-027-partner-onboarding.md), [ADR-028-multitenant-monitoring.md](ADR-028-multitenant-monitoring.md), [roles-and-access-matrix.md](../roles-and-access-matrix.md), [c2-to-be.puml](../diagrams/c2-to-be.puml)

## Контекст

На базовой диаграмме контейнеров IAM присутствует как **один абстрактный контейнер `IAM / SSO`** ("OAuth2/OIDC, RBAC, SSO, least privilege", ADR-018) - этого недостаточно для мультитенантной платформы. Задача требует **IAM-систему с ролевым доступом и SSO** и таблицу ролей с уровнями доступа к данным.

Дополнительные рамки:

- **Мультитенантность** (ADR-025): доступ всегда ограничен тенантом и регионом; тенант - первый класс в модели авторизации.
- **Резидентность идентификационных данных** (ADR-013/017): учётные записи и персональные атрибуты пользователей - такие же PII, как и бизнес-данные, и должны храниться в суб-регионе пользователя.
- **Zero-trust** (ADR-018): доверия "внутри" нет; токен проверяется на каждом шаге, а авторизация - не только на шлюзе.
- Действующий ландшафт: Django/Python-сервисы, API Gateway/BFF, собственные мобильные приложения (iOS/Android/Huawei), веб-портал и админ-панель (Django Admin), партнёрский self-service портал (ADR-027).

## Требования

1. Ввести **единую IAM-систему** с **SSO** для всех типов пользователей: пассажиры, водители, корпоративные клиенты, администраторы платформы, сотрудники партнёра-тенанта.
2. Обеспечить **ролевой доступ (RBAC)** с **атрибутной детализацией (ABAC)** по `tenant_id`, `region`, `data-classification` (ADR-025).
3. Обеспечить **резидентность** идентификационных данных: реестр пользователей региона хранится в регионе; PII пользователей не покидает суб-регион.
4. Обеспечить **SSO** между приложениями (мобильные, веб, админка, партнёрский портал) без повторного входа.
5. Реализовать **machine-to-machine** аутентификацию для партнёрских API и сервисных аккаунтов.
6. Обеспечить **least privilege**, **step-up/MFA для привилегированных ролей**, короткоживущие токены и **аудит всех аутентификаций/авторизаций** (ADR-018).
7. Не создавать **глобальную единую точку отказа** IAM; согласовать с геомаршрутизацией (ADR-015) и DR (ADR-016).
8. Интегрировать IAM с **онбордингом** (автосоздание realm/организаций/клиентов - ADR-027) и **отгрузкой ролей в таблицу доступа** ([roles-and-access-matrix.md](../roles-and-access-matrix.md)).

## Решение

### Выбор: Keycloak как IAM/IdP

Выбран **Keycloak** (open source, self-hosted/управляемый) как **OIDC/OAuth2-провайдер**, SSO-хаб и движок RBAC:

- зрелая поддержка **OIDC/OAuth2** (Authorization Code + PKCE, client credentials, token exchange), SAML и федерации IdP (задел для enterprise-партнёров);
- **realm'ы, группы, organization, client scopes, role mappings, protocol mappers** - естественно ложатся на мультитенантность и claims;
- self-hosted → **резидентность** (разворачивается в каждом регионе) и cloud-agnostic, без привязки к вендору managed-IAM;
- в отличие от "домашнего" решения на Django, даёт SSO, федерацию, MFA, consent, сессии и админ-UI "из коробки" и не отвлекает продуктовые команды.

### Топология: realm-per-region + сервисные realm'ы

```text
        +---------------------------------------------------+
        |            Global (platform) plane                 |
        |  Keycloak platform realm: платформенные админы,    |
        |  SRE/SOC automation, service accounts              |
        +---------------------------------------------------+
                     |  (OIDC / token exchange при аудите)
   +-----------------+------------------+------------------+
   |                 |                  |                  |
 base realm     sea-sg realm       sea-id realm       sa-br / sa-cl realms
 (Россия/СНГ)   (Сингапур)         (Индонезия)        (Бразилия / Чили)
   |                 |                  |                  |
 Sub-region Keycloak cluster (HA, БД с репликой в DR-паре макро-региона)
   |                 |                  |                  |
 Пассажиры/водители/корп-клиенты/админы тенантов региона (PII остаётся в регионе)
```

| Решение | Обоснование |
|---------|-------------|
| **Realm на суб-регион** (`base`, `sea-sg`, `sea-id`, `sa-br`, `sa-cl`) | Резидентность идентичностей (ADR-013/017/024); изоляция blast-radius по регионам; локальная задержка логина |
| **Отдельный глобальный platform realm** | Платформенные администраторы, автоматизация (CI/CD, онбординг-оператор), break-glass; не содержит массовых PII |
| **Раздельные хранилища realm'ов** | Региональный realm - в **БД региона** (резидентность идентичностей); platform realm - в **отдельной БД hub-региона**. Глобальный realm **не** пишет в региональные БД (иначе cross-region write и нарушение резидентности) |
| **Тенанты внутри realm через Organizations/группы + `tenant_id` mapper** | Один realm на регион при множестве тенантов - управляемо; `tenant_id` попадает в токен как claim |
| **Keycloak-кластер с БД в регионе** | HA внутри макро-региона (реплика в DR-паре, ADR-014/016); нет глобального SPOF; локальные сессии |
| **Отдельный realm для silo-тенантов (опция)** | Для тенантов с повышенными требованиями - полная изоляция конфигурации и IdP (расширение, не дефолт) |
| **Federation/BYO-IdP (SAML/OIDC) - задел** | Enterprise-партнёры смогут подключить корпоративный IdP; базовый релиз - нативные учётные записи Keycloak + OIDC |

### Аутентификация и SSO

- **Протокол: OIDC для всех клиентов** (ADR задачи - OIDC-везде):
  - мобильные приложения (пассажир/водитель) - **public client, Authorization Code Flow + PKCE**, refresh rotation;
  - веб-портал, админ-панель, партнёрский портал - **confidential client**, OIDC + **back-channel logout**;
  - API Gateway/BFF - **resource server**: локальная валидация JWT по **JWKS** (кеш ключей) + introspection для высокорисковых операций;
  - партнёрские API и сервис-сервис - **client credentials** (service accounts, scopes).
- **SSO**: единая сессия Keycloak + **token exchange** между клиентами; вход один раз, доступ ко всем приложениям GoFuture (и порталу тенанта), включая кросс-приложение без повторной аутентификации.
- **Телефон/OTP** для пассажиров и водителей реализуется как **аутентификационный flow Keycloak** (SMS-OTP). **Разрыв циклической зависимости:** отправка OTP идёт **выделенным путём** - Keycloak SPI/клайент вызывает SMS-провайдера напрямую или через **отдельный SMS-gateway с собственным service account**, а не через основной Notification Service (иначе Keycloak → Notification → Keycloak: Notification сам аутентифицируется в Keycloak). Это устраняет рантайм-цикл при недоступности IAM.
- **MFA (TOTP/WebAuthn)** - **обязательная политика для привилегированных ролей** (платформенные админы, админы тенантов, финансовые роли, break-glass); для массовых пользователей - по риск-политике. *Решение сознательно расширяет подтверждённый ответ "OIDC для всех клиентов" (этот ответ фиксирует протокол, а не отказ от MFA): MFA для привилегированных - базовое требование ADR-018; подлежит подтверждению владельцем продукта, при отклонении - понижается до риск-политики.*
- **Кросс-региональный вход**: пользователь аутентифицируется в **realm своего региона** (маршрутизация по гео-роутингу, ADR-015); сессия привязана к резидентному realm, а данные - к суб-региону субъекта. Вход в "чужой" realm - только как гостевой для бизнес-операций тенанта присутствия и не меняет резидентность PII.
- **Требования к Keycloak**: версия с поддержкой **Organizations** и Organizations-scoped RBAC (модель партнёров-тенантов); при ограничениях версии - fallback на группы + `tenant_id`-маппер (функциональная эквивалентность по claims). Версии фиксируются и обновляются по регламенту без breaking-changes для контракта claims.
- **Сессии**: короткий access token (5–15 мин), refresh с ротацией и привязкой к устройству; silent SSO через iframe/refresh для веб.
- **Совместимость**: сумматорный claims-контракт токена (см. ниже) документируется как публичный контракт; эволюция claims - по правилам совместимости (ADR-004).

### Авторизация: RBAC + ABAC

**RBAC даёт роли, ABAC - их мультитенантную и региональную проекцию.** Решение о доступе = `role ∪ attribute`:

- **RBAC**: роли (realm/client roles) выдаются пользователям/группам; роли отображаются в **permissions** (scopes) на ресурсы;
- **ABAC-атрибуты** (в токене и в сервисах): `tenant_id`, `region` (макро) и `sub_region` (**суб-регион** - граница тенанта, доступа и резидентности, ADR-013/025), `clearance` (**набор разрешённых классов**, напр. `{L1, L5}`; не скалярный максимум - см. матрицу), `corporate_id`/`fleet`, тип субъекта (passenger/driver/staff);
- **Правило доступа**: `grant iff (role_permits(resource, action) AND attr_tenant_matches(resource.tenant) AND attr_subregion_matches(resource.sub_region) AND resource.classification ∈ clearance)`. Границы доступа по региону определяются **суб-регионом**: тенант не пересекает границу суб-региона. **`clearance` - множество, а не "максимум":** несплошные наборы (`{L1, L5}`) нельзя выразить скаляром, иначе L5-роль получит и L3/L4; класс `L5 (Audit)` - отдельная ось, не "уровень выше L4" (см. [roles-and-access-matrix.md](../roles-and-access-matrix.md)).

**Точки принуждения (defense-in-depth, ADR-025/018):**

| Где | Что проверяется | Результат |
|-----|-----------------|-----------|
| API Gateway | подпись/срок/issuer токена, `tenant_id` vs запрошенный ресурс, scope, rate limit | отсечение на входе, 401/403 |
| Сервисы | permissions (scope) + атрибуты (tenant/region/clearance) + tenant context | бизнес-авторизация |
| Данные | RLS по `tenant_id` (ADR-025) | последний барьер, fail-closed |
| Аналитика/BI | RLS/тенантные представления, маскирование PII | нет cross-tenant доступа |
| Админ-действия | отдельные admin-scopes + MFA + аудит + 4-eyes для критичных | контроль привилегий |

**Клиентские роли** (клиент `gateway`/сервисы) маппятся в permissions; **типовые роли и уровни доступа к данным** сведены в [roles-and-access-matrix.md](../roles-and-access-matrix.md).

**Опциональный policy-engine (OPA/Cedar)** выносит сложные ABAC-правила из кода; базовый релиз - библиотека авторизации (единый модуль), OPA - при росте сложности (см. "Альтернативы").

### Контракт токена (упрощённо)

| Claim | Значение | Кто проверяет |
|-------|----------|---------------|
| `iss` | realm региона | все (issuer binding) |
| `sub` | пользователь/клиент | все |
| `tenant_id` | тенант (ADR-025); **отсутствует или = `*` только у платформенного плана** (никогда для тенантных операций, где нужен конкретный тенант); cross-tenant чтение выполняется только break-glass-ролью БД (ADR-025) | шлюз, сервисы, RLS |
| `region` / `sub_region` | макро-регион и **суб-регион** пользователя (граница доступа/резидентности) | шлюз, сервисы |
| `roles` / `scope` | роли и permissions | шлюз, сервисы |
| `clearance` | **набор** разрешённых классов данных (напр. `{L1,L5}`); не скалярный максимум | сервисы, BI |
| `mfa` / `acr` | факт step-up-аутентификации | привилегированные операции |
| `exp`/`aud` | короткий срок, аудитория сервиса | все |

### Секреты, интеграции, аудит и эксплуатация

- **Секреты Keycloak** (БД, client secrets, ключи подписи) - в **Vault** per-region (ADR-018); ротация ≤ 90 дней; ключи подписи - ротация и публикация JWKS.
- **mTLS** между Keycloak/шлюзом/сервисами (service mesh, ADR-018).
- **Аудит**: все события login/token/consent/admin-операции → **SIEM** и **неизменяемый аудит-стор (WORM ≥ 1 год)** (ADR-018). Отдельно - аудит выдачи/изменения ролей (кто, кому, когда, почему).
- **Наблюдаемость IAM** (ADR-028): метрики логинов, ошибок аутентификации, latency token-эндпоинтов, аномалии (brute-force, невозможные путешествия), per-tenant разрез.
- **DR**: realm-кластер в DR-паре макро-региона; восстановление realm из бэкапа; при отказе региона - переключение на пару (ADR-016) с сохранением резидентности (идентичности не покидают макро-регион).
- **Роли и права как код**: realm/клиенты/роли/мапперы провижинятся декларативно (Keycloak admin API + IaC, ADR-027), ревью через Git.

## Альтернативы

1. **Собственная IAM на Django.** Переиспользует навыки команды, но требует строить SSO, федерацию, MFA, OIDC-конформанс и админ-UI; высокая стоимость и риск; не даёт выигрыша в сроке подключения партнёров.
2. **Управляемые SaaS-IAM (Auth0/Okta/Entra ID).** Меньше операционной нагрузки, но **резидентность и облачная независимость** под вопросом (PII идентичностей в другом регионе), стоимость на массовых пользователей высока; противоречит cloud-agnostic и локальным нормам.
3. **Единый глобальный realm Keycloak.** Простое управление, но нарушает резидентность идентичностей, слабо изолирует тенантов и создаёт глобальный SPOF.
4. **Realm на каждого тенанта.** Максимальная изоляция конфигурации, но при десятках/сотнях тенантов - десятки/сотни realm'ов: операционная и ресурсная нагрузка; консолидируется в organizations внутри регионального realm (+ отдельный realm только для silo-тенантов).
5. **Только RBAC (без ABAC).** Проще, но не выражает тенантную/региональную/классификационную привязку и провоцирует "ролевой взрыв".
6. **Только ABAC/policy-engine.** Гибко, но избыточная сложность для базовых сценариев и высокий порог входа; выбран гибрид с возможностью вынести правила в OPA позже.
7. **Авторизация только на шлюзе.** Быстро, но нарушает zero-trust: сервис, вызванный в обход шлюза, окажется без проверки прав; неприемлемо.

## Компромиссы и риски

- **Keycloak добавляет операционную нагрузку** (кластеры per-region, БД, обновления, тюнинг); митигация - IaC, Helm, единый runbook, managed-хостинг там, где он резидентен.
- **Резидентность realm'ов** усложняет федерацию между регионами (платформенные админы, глобальные группы); митигация - platform realm + token exchange, минимальные глобальные данные.
- **Краткоживущие токены** повышают частоту обновлений; митигация - refresh rotation, silent SSO, кеш JWKS.
- **`tenant_id`/`clearance` в токене устаревают** при смене прав (до истечения токена); митигация - короткий TTL + отзыв сессии/токена (revocation) для критичных изменений.
- **Сложный ABAC** может быть труднопроверяемым; митигация - единый модуль решений, тесты политик, аудит отказов, постепенный переход к OPA.
- **OTP/MFA** добавляет трение и стоимость SMS; митигация - risk-based step-up, WebAuthn/TOTP для staff, OTP только там, где нужен.
- **Единая точка доверия - подпись/ключи Keycloak:** компрометация ключа подписи критична; митигация - HSM/надежное хранение в Vault/KMS, короткий срок жизни ключей, мониторинг аномалий, изоляция регионов.
- **Партнёрский self-service** требует делегированного администрирования; риск эскалации привилегий внутри тенанта; митигация - лимиты ролей тенанта, "неизменяемые" платформенные роли, 4-eyes на критичные операции.

## Допущения

- Целевые провайдеры допускают размещение Keycloak и его БД в каждом суб-регионе с HA и репликой в DR-паре.
- Согласован baseline-набор ролей ([roles-and-access-matrix.md](../roles-and-access-matrix.md)); он расширяется per-tenant без нарушения платформенных ролей.
- Federated SSO с корпоративными IdP (SAML/OIDC, BYO-IdP) - **следующая итерация**; архитектура к ней готова, но базовый релиз - нативные учётные записи Keycloak + OIDC.
- Партнёрские service accounts выдаются при онбординге автоматически (ADR-027).
- Юридическая валидация локализации идентификационных данных - в рамках ADR-017.
