# Матрица ролей и уровней доступа к данным (мультитенантная платформа)

Артефакт определяет роли, скоуп доступа (тенант/регион) и **уровни доступа к данным** для мультитенантной платформы "GoFuture" с IAM на Keycloak (ADR-026) и гибридной изоляцией данных (ADR-025).

Связанные ADR: [ADR-025](adr/ADR-025-tenant-isolation.md), [ADR-026](adr/ADR-026-iam-keycloak-rbac.md), [ADR-027](adr/ADR-027-partner-onboarding.md), [ADR-028](adr/ADR-028-multitenant-monitoring.md), [ADR-017](../Task3/adr/ADR-017-compliance.md), [ADR-018](../Task3/adr/ADR-018-security-landscape.md).

---

## 1. Классификация данных (уровни доступа)

| Уровень | Класс | Примеры данных | Как выдаётся |
|---------|-------|----------------|--------------|
| **L0** | Public | Публичные тарифы, зоны, маркетинговые данные, статус платформы | Свободно / анонимно |
| **L1** | Internal | Агрегаты и метрики, конфигурация, справочники, телеметрия, деидентифицированная аналитика | Аутентифицированный доступ по роли |
| **L2** | Confidential | Токенизированная/маскированная PII (частичные контакты, ID), внутренние идентификаторы | Маскирование по умолчанию; unmask только с обоснованием |
| **L3** | Restricted (PII) | Полная PII: ФИО, телефон, e-mail, гео-история, документы водителя, адреса | Least privilege + JIT-повышение + аудит каждого доступа |
| **L4** | Financial / Regulated | Платежи, выплаты, реквизиты, токены карт (PCI), финансовые транзакции | Строгое разделение обязанностей, MFA, 4-eyes на выплаты |
| **L5** | Audit / Governance | Аудит-логи, access-логи, security-события, DSR, data map | Read-only (immutable), выдача мала и аудируется |

**Правило комбинирования:** доступ = `роль ∧ тенант ∧ суб-регион ∧ классификация`:
`grant ⇔ perm(resource, action) ∧ tenant(resource)=tenant(actor) ∧ subRegion(resource)=subRegion(actor) ∧ class(resource) ∈ clearance(actor)` (ADR-026). Границы доступа по региону определяются **суб-регионом** (тенант не пересекает границу суб-региона, ADR-013/025).

> **Классы выдаются набором, а не "максимумом".** У ролей классы данных несплошные (например, Security/SOC - `{L1, L5}`, Compliance - `{L1, L2, L5}`, External Auditor - `{L1, L5}`), поэтому `clearance(actor)` - это **множество разрешённых классов**, а не скалярный "максимальный уровень". Скалярный максимум ошибочно выдал бы L5-роли доступ к L3/L4 (сырая PII, финансы). Класс **L5 (Audit/Governance)** - **отдельная ось** (аудит/комплаенс-данные), а не "уровень выше L4": доступ к L5 не влечёт доступ к L3/L4.

**Скоупы:**

- `own` - только собственные данные субъекта;
- `own-tenant` - данные своего тенанта (в границах **суб-региона** тенанта);
- `own-company` - данные своей корпорации (B2B);
- `cross-tenant-anonymized` - только деидентифицированные агрегаты по всем тенантам;
- `platform` - вне границ тенанта (платформенные операции; для сырых PII - только break-glass).

## 2. Роли и уровни доступа к данным (основная таблица)

### 2.1 Платформенные роли (GoFuture)

| Роль | Скоуп | Классы данных | Разрешённые операции | MFA / step-up | Условия и ограничения |
|------|-------|---------------|----------------------|---------------|-----------------------|
| **Platform Super Admin** (break-glass) | `platform` | L0–L5 | Полный административный доступ, управление ролями, аварийные операции | **Обязательно** (WebAuthn) + 4-eyes | Выдаётся на время, только по инциденту; cross-tenant чтение - **только через break-glass-роль БД с `BYPASSRLS`** (ADR-025); каждый доступ - в WORM-аудит; иначе роль заблокирована |
| **Platform Operations Admin** | `platform` (управление тенантами) | L0–L2 (метаданные тенантов), не бизнес-PII | Создание/изменение/приостановка тенантов, квоты, конфигурация, фича-флаги | **Обязательно** (TOTP) | Не видит сырые PII и финансы; действия аудируются |
| **SRE / Platform Engineer** | `platform` (инфраструктура) | L0–L1 (+L2 маскированно) | Метрики, логи, трейсы, инфраструктура, скейлинг, runbook | **Обязательно** (TOTP) | Доступ к сырым PII не предусмотрен; unmask - только через поддержку/JIT |
| **Security / SOC Analyst** | `platform` (безопасность) | L1, L5 (+L2/L3 при расследовании, JIT) | Чтение security-событий, аудита, корреляция, блокировки | **Обязательно** | Read-only по умолчанию; доступ к PII - по инциденту с записью в аудит |
| **Compliance Officer / DPO** | `platform` (комплаенс) | L1, L5, L2 (data map) | Аудит, DSR, records of processing, проверки | **Обязательно** | Сырые PII - только в рамках DSR с правовым основанием |
| **FinOps / Billing Analyst** | `platform` (агрегаты) | L1 (+ L4 сводно) | Биллинг и потребление на тенанта (агрегированно), стоимость | По политике | Не видит PII и персональные транзакции; только агрегаты |
| **Onboarding Approver (KYC/Compliance Reviewer)** | `platform` (онбординг) | L0–L2 (заявочные/юр. данные партнёра) | Approve/Reject/NIH заявок онбординга (ADR-027), версии решений | **Обязательно** | 4-eyes на approve; SLA-таймеры; каждое решение - в аудит; не даёт доступ к бизнес-данным тенанта |
| **Security Approver (онбординг)** | `platform` (онбординг/безопасность) | L1, L5 (+L2 по заявке) | Security-ревью и approve заявки; проверка требований изоляции | **Обязательно** | Совмещается с ролью Security/SOC при разделении обязанностей; решение фиксируется в WORM |
| **Business Approver (онбординг)** | `platform` (онбординг/бизнес) | L0–L1 (коммерческие условия заявки) | Финальный бизнес-approve заявки: тариф/SLA, tier изоляции, квоты, коммерческие условия | **Обязательно** | Заключительное звено approval-workflow (ADR-027); 4-eyes на approve; доступ к бизнес-данным тенанта не даёт |
| **Fraud / Risk Analyst** | `platform` (антифрод) | L1–L2 (риск-скоры, признаки), unmask до L3 по JIT | Правила/модели антифрода, разбор инцидентов, решения | **Обязательно** | PII - минимально необходимая, по JIT; должность из домена Fraud; аудит доступа |
| **Data / ML Engineer** | `platform` (данные/ML) | L1–L2 (деидентифицированные слои) | Пайплайны, признаки, обучение/инференс, data governance | **Обязательно** | Сырая PII недоступна (работа на деидентифицированных данных, ADR-024); JIT - исключение |
| **External Auditor / Regulator** | `platform` (аудит) | L1, L5 | Read-only: аудит, комплаенс, отчёты (Supervised Access) | По политике + supervision | Time-boxed доступ, сопровождается сотрудником, полный аудит сессии; бизнес-данные не выдаются |
| **Platform Support Agent** | `platform` (тенанты) | L0–L2, unmask до L3 по JIT | Поддержка пользователей, просмотр состояния, диагностика | **Обязательно** | Unmask PII - с тикетом и обоснованием; JIT-окно; аудит |

### 2.2 Роли тенанта (партнёр-оператор)

| Роль | Скоуп | Классы данных | Разрешённые операции | MFA / step-up | Условия и ограничения |
|------|-------|---------------|----------------------|---------------|-----------------------|
| **Tenant Admin** | `own-tenant` | L0–L3 своих данных; L4 (финансы тенанта) | Управление пользователями/ролями тенанта, конфигурация, брендинг, API-ключи | **Обязательно** | Не может выдать права выше своего потолка; не видит другие тенанты и платформенные настройки. **SoD:** для средних/крупных тенантов роль **разделяется** на `Tenant IAM Admin` (пользователи/роли, без L4) и `Tenant Finance` (L4); совмещение L3+L4+IАМ-администрирования в одном лице запрещено |
| **Tenant Operations / Dispatcher** | `own-tenant` | L1–L3 (операционные данные поездок и водителей) | Управление сменами/матчингом, просмотр поездок, инциденты | **Обязательно** (политика) | PII водителя/пассажира - в объёме, нужном для операции; unmask с причиной |
| **Tenant Finance / Accountant** | `own-tenant` | L4 (выплаты/счета тенанта), L1 | Просмотр и выгрузка выплат/счетов, сверка, подтверждение | **Обязательно** + 4-eyes | Изменение реквизитов - dual control; полный аудит |
| **Tenant Analyst** | `own-tenant` | L1, L2 (деидентифицированные агрегаты) | Отчёты и дашборды своего тенанта | По политике | Сырая PII недоступна; только агрегаты/витрины |
| **Tenant Support Agent** | `own-tenant` | L0–L2, unmask до L3 по JIT | Поддержка пользователей тенанта | **Обязательно** | Маскирование по умолчанию; JIT + аудит на unmask |
| **Tenant API Client** (machine-to-machine) | `own-tenant` | L0–L2 по выданным scopes | Вызовы партнёрского API в рамках scopes | Client credentials (не пользователь) | Scopes выдаются при онбординге; ротация секретов (Vault) |

### 2.3 Роли конечных пользователей

| Роль | Скоуп | Классы данных | Разрешённые операции | MFA / step-up | Условия и ограничения |
|------|-------|---------------|----------------------|---------------|-----------------------|
| **Passenger** | `own` | L0, свои L2/L3, свои L4 (платежи по своим поездкам) | Заказ/отмена поездки, история, способы оплаты, профиль | По риск-политике (OTP) | Не видит данные третьих лиц и водителей за пределами поездки |
| **Driver** | `own` | L0, свои L2/L3, свои L4 (выплаты) | Приём/выполнение заказов, смены, заработок, документы | По риск-политике (OTP) | Видит пассажира только в рамках активной поездки |
| **Corporate Manager** | `own-company` | L0–L2 по поездкам сотрудников, L4 (счета компании) | Политики поездок, лимиты, отчёты, счета компании | **Обязательно** (SSO-корп) | Данные сотрудников - в объёме бизнес-функции; не видит других компаний |
| **Corporate Bookkeeper / Approver** | `own-company` | L1, L4 (финансы компании) | Сверка и согласование счетов/платежей | **Обязательно** | Dual control на платежи; без доступа к PII сотрудников кроме суммы |

**Корпорация ↔ тенант.** Корпоративный клиент (`corporate_id`) - аккаунт **внутри одного тенанта и суб-региона** (корпорация не пересекает границу тенанта, ADR-025); в токене одновременно присутствуют `tenant_id` и `corporate_id`. Скоуп `own-company` дополнительно сужает `own-tenant` до данных конкретной корпорации, но **не расширяет** его за пределы тенанта/региона: `own-company ⊂ own-tenant`. Один сотрудник может состоять в нескольких корпорациях одного тенанта - контекст (тенант и корпорация) выбирается явно на сессию (ADR-026).

### 2.4 Сервисные (machine) идентичности платформы

Не пользователи, а аутентифицированные сервисы (mesh/SPIFFE, service accounts). Не наследуют пользовательские роли и не имеют интерактивных сессий.

| Идентичность | Скоуп | Классы данных | Разрешённые операции | Аутентификация | Условия |
|--------------|-------|---------------|----------------------|----------------|---------|
| **Service identity (доменный сервис)** | `platform` (сервис-сервис) | L0–L3 в объёме вызова | Обработка запросов/событий в рамках tenant context | mTLS (SPIFFE) + token | Tenant context обязателен (fail-closed); без него - отказ (ADR-025) |
| **Provisioning Operator identity** | `platform` (управление ресурсами) | L0–L1 (метаданные), без бизнес-данных | Создание/реконсиляция ресурсов тенанта | mTLS + Keycloak client credentials | Только по манифесту; изменения аудируются (ADR-027) |
| **CI/CD identity** | `platform` (доставка) | - (нет данных) | Деплой образов/конфигураций | OIDC (workload identity) | Нет доступа к данным и секретам рантайма (Vault-пути разделены) |
| **DSR executor identity** | `platform` (права субъектов) | L3/L4 (точечно, по запросу) | Исполнение DSR: доступ/удаление/crypto-shredding | mTLS + client credentials | Только в рамках обращения субъекта; полный аудит (ADR-017/025) |
| **Metering identity** | `platform` (учёт) | L0–L1 (usage) | Приём usage-событий | client credentials | Идемпотентная запись, без чтения бизнес-данных (ADR-027) |

## 4. Принципы применения

1. **Deny by default** и **fail-closed**: отсутствие явного разрешения - отказ (ADR-025/026).
2. **Least privilege + JIT**: доступ к L3/L4/L5 выдаётся на время и по обоснованию; постоянное закрепление не предусмотрено. Cross-tenant доступ платформенных ролей - только через break-glass-роль с `BYPASSRLS` под MFA + 4-eyes и WORM-аудитом (ADR-025).
3. **Разделение обязанностей**: финансовые операции - 4-eyes; admin-роли не совмещают IAM-администрирование и аудит; **Tenant Admin** для крупных тенантов разделяется на IAM-администрирование (без L4) и финансы (L4) - совмещение запрещено.
4. **Маскирование по умолчанию** для L2; unmask - событие аудита.
5. **Тенант и регион - жёсткие границы**: роли тенанта никогда не дают доступа за пределы своего тенанта и суб-региона (ADR-025).
6. **Изменения ролей и прав - аудируемы** (кто/кому/когда/почему) и ведутся как код (ADR-026/027).
7. **Роли не пересекают тенантов**: один пользователь может иметь роли в нескольких тенантах, но контекст выбирается явно (`tenant_id` в токене) и не суммируется в одном запросе.
8. **Сервисные идентичности не наследуют пользовательские роли** и работают только в tenant context (fail-closed); их права описываются разделом 2.4 и выдаются при провижининге (ADR-027).
9. **Внешний доступ (аудитор/регулятор)** - только supervised, time-boxed и read-only; выдача бизнес-данных сверх L5 не допускается без правового основания.
10. **Событийный поток (Kafka) в pooled общий на чтение**: любой консьюмер топика видит события всех тенантов, поэтому изоляция обеспечивается обязательным tenant-контекстом консьюмера (fail-closed), ACL на consumer groups, токенизацией PII в конверте и отдельными топиками для `silo` (ADR-025).
