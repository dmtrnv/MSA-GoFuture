## Контекст

"GoFuture" строит единую платформу для сбора, обработки и анализа данных под ML-модели **динамического ценообразования**, **прогнозирования спроса** и **обнаружения мошенничества**. Платформа должна собирать данные из всех микросервисов.

Текущий ландшафт:
- **ClickHouse** уже используется как аналитическая БД;
- Обработка данных - **Spark/Flink**, ETL-процессы;
- BI - **DataLens**;
- Источники данных уже стандартизованы: `database-per-service` + **Transactional Outbox** → **Kafka** с моделью доменных событий и региональным партиционированием (ADR-006, ADR-007, ADR-008, ADR-011).

Ограничения и драйверы:
- **Объём и разнородность**: 500 тыс. конкурентных поездок, сверхвысокочастотный поток `DriverLocationUpdated`, финансовые и антифрод-события;
- **ML требует обучающих данных**: нужны "сырые" и переигрываемые данные за длительный период, а не только агрегаты;
- **Эволюция схем**: контракты событий меняются (Avro BACKWARD, ADR-007), хранилище не должно ломаться при добавлении полей;
- **Точность во времени (point-in-time)** для обучения без утечек будущего;
- **Резидентность PII** (NFR-C-01, ADR-014, ADR-017) и **мультирегион**;
- **Стоимость** (NFR-COST-01/02) и **cloud-agnostic** (ADR-013).

## Требования

1. Единое хранилище "сырых" и переигрываемых данных за длительный срок (replay, ML-обучение, аудит).
2. Разделение ответственности: дешёвое масштабируемое хранение vs. быстрый OLAP-serving.
3. Поддержка **эволюции схем** и **time travel** (point-in-time) без перезаписи истории.
4. Пакетная и потоковая обработка поверх одного хранилища (Spark/Flink/dbt).
5. Отдельные хранилища для **offline** (обучение) и **online** (инференс) доступа к признакам.
6. Региональная изоляция данных (PII остаётся в регионе), глобальный слой - только деидентифицированное.
7. Контроль стоимости: хранение в object storage, а не в дорогом OLAP.
8. Переносимость между облаками (нет привязки к проприетарному DWH).

## Решение

### Слоистая модель Lakehouse (medallion) на Object Storage + Iceberg

Выбираем **Lakehouse**: хранение фактов и признаков в **S3-совместимом Object Storage** в табличном формате **Apache Iceberg**, а **ClickHouse** оставляем как **serving/OLAP-слой** для BI и приложений.

| Слой | Содержимое | Формат / хранение | Регион |
|------|------------|-------------------|--------|
| **Bronze (raw)** | Доменные события со стабильной структурой (envelope + payload + `schema ID`), append-only; **PII-поля токенизированы на ingest** (per-subject токен); CDC-снимки справочников | Iceberg (Parquet) на Object Storage | Регион источника |
| **Silver (cleansed)** | Дедуплицированные, валидированные, нормализованные доменные таблицы; PII **только в токенизированном/маскированном** виде | Iceberg на Object Storage | Регион источника |
| **Gold (serving marts)** | Витрины для BI + **offline-таблицы признаков** для ML (материализуются из silver) | ClickHouse (витрины) + Iceberg (feature/offline) | Регион + глобальные агрегаты |
| **Online feature store** | Онлайн-признаки для инференса | Redis | Регион |

Принципы:
- **Object Storage** - источник долговременного хранения и replay; дешёвый, неограниченно масштабируемый, не хранит "горячие" запросы.
- **ClickHouse** - **не** хранит сырые данные; в нём только смоделированные витрины (gold) для BI/real-time аналитики (быстрые агрегации).
- **Apache Iceberg** как табличный формат: ACID-коммиты, **эволюция схем** (add/drop/rename без перезаписи), **time travel** и snapshots (point-in-time для ML), скрытое партиционирование, совместимость с **Spark, Flink**.
- **Единый писатель на слой**: **bronze** пишет только ingest; **silver** - Flink (streaming), Spark допускается лишь для **off-path** пересборки/backfill (взаимоисключающе с потоковой записью); витрины **gold** - dbt/Flink; **offline-признаки** (Iceberg, gold-уровень) материализуются из silver (Spark/dbt).

### Вычислительные движки поверх lakehouse

- **Flink** (ADR-009) - потоковая обработка: near-real-time silver/gold и оконные признаки (surge, hot-zone), запись в Iceberg и ClickHouse через Iceberg/Flink sink.
- **Spark** - batch: переработка/backfill истории, построение больших обучающих датасетов, агрегации по всему периоду.
- **dbt** - SQL-моделирование витрин gold на ClickHouse (staging → marts), тесты качества данных (ADR-023).
- **Оркестрация** - Airflow (DAG-и batch-заданий и пайплайнов обучения, ADR-021).

Разделение: **streaming (Flink) - свежесть**, **batch (Spark) - полнота/корректность и ML-датасеты**, **SQL (dbt) - витрины**.

### Доставка gold-витрин в ClickHouse

- **Чтение silver из Iceberg в ClickHouse** - через **Iceberg table engine** (read-only); dbt выполняет модели поверх этих таблиц.
- **dbt** материализует витрины как **штатные (incremental) таблицы ClickHouse**, а не как внешние Iceberg-таблицы - это даёт быстрые BI-запросы и локальные индексы/движки ClickHouse.
- **Тяжёлые пересборки/backfill** витрин выполняет **Spark**, загружая gold в ClickHouse батчами (идемпотентно, по партициям).
- **Потоковые витрины** (surge, hot-zone) пишет **Flink** напрямую в ClickHouse, минуя batch; reconciliation между Flink- и dbt-витринами - DQ-проверка (ADR-023).

### Размещение и партиционирование

- Бакеты и таблицы - **per-region** (`subRegionId`, ADR-013); ключ данных несёт `regionId` (совпадение с партиционированием Kafka, ADR-008).
- Партиционирование таблиц: `regionId` → `event_date` (день) → при необходимости `domain`. Для `driver.location` - короткое хранение в детальном виде + агрегаты за длительный срок.
- **Iceberg catalog** - REST catalog / metastore (единый сервис метаданных таблиц per-region).
- **Обслуживание таблиц** (compaction, snapshot expiration, orphan files) - регулярные джобы; без этого - деградация из-за мелких файлов.

## Альтернативы

1. **Только ClickHouse (как сейчас), без lakehouse.** Проще и уже есть, но дорого хранить "сырые данные" за длительный срок, слабее replay/backfill и эволюция схем; обучающие датасеты собираются ad-hoc.
2. **Hive/Parquet на Object Storage без Iceberg.** Дёшево, но нет ACID-коммитов, time travel и корректной конкурентной записи из Flink/Spark.
3. **Delta Lake вместо Iceberg.** Сопоставим по возможностям; Iceberg выбран из-за нейтральности к движкам (Spark + Flink) и скрытого партиционирования.
4. **Проприетарный managed DWH (Snowflake/BigQuery-класс).** Меньше операционной нагрузки, но vendor lock-in, стоимость и вопросы резиденции данных.
5. **Kafka с tiered storage как долговременное хранилище.** Retention не заменяет аналитическое хранилище; нет колоночных запросов, дорого для больших сканов.
6. **Единый DWH без serving-слоя.** Один инструмент, но OLAP-запросы BI и низколатентный инференс конкурируют за ресурсы.

## Компромиссы и риски

- **Два слоя хранения** (Object Storage + ClickHouse) → необходимость синхронизации и дублирования данных; митигация - Flink/dbt как единственный путь записи витрин, идемпотентная загрузка.
- **Операционная зрелость Iceberg**: нужны регламенты compaction/snapshot-expiration, иначе "мелкие файлы" и рост метасторы.
- **Задержка batch-слоя**: витрины gold для BI могут отставать; near-real-time обеспечивает Flink, но не все метрики.
- **Стоимость compute** Spark/Flink при переработке истории; митигация - автоскейл и инкрементальные модели.
- **Качество сырого слоя**: "сырые данные" содержит ошибки и дубликаты - их обрабатывают dedup/DQ на переходе bronze→silver (ADR-023).
- **Рост объёма гео-потока** (location) - митигация: отдельный топик/пайплайн, короткое детальное хранение, агрегаты надолго.
- **Согласованность определений между Flink (stream) и Spark/dbt (batch)** - риск расхождения метрик; митигация: единая семантика в dbt/Iceberg-таблицах, сверка агрегатов (ADR-023).

## Допущения

- Managed S3-совместимый Object Storage доступен в каждом суб-регионе и поддерживает требуемую пропускную способность.
- Версии Flink/Spark совместимы с выбранной версией Iceberg; Iceberg REST catalog разворачивается per-region в HA.
- ClickHouse используется как serving-слой, а не как долговременное хранилище сырых данных.
- Глобальный слой аналитики оперирует только деидентифицированными/агрегированными данными (ADR-014, ADR-017).
