## Контекст

Требуется интеграции пайплайна данных с **BI-инструментами**. В компании уже используется **DataLens** и **ClickHouse** как аналитическая БД. Нужно определить, как BI-потребители получают данные из новой платформы данных (ADR-019) без прямой работы с сырыми слоями.

Заинтересованные стороны:
- **корпоративные менеджеры и бухгалтеры** (отчёты по поездкам и выплатам);
- **продуктовые команды** (метрики домена, воронки, качество);
- **data-аналитики** (самообслуживание).

Ограничения: низкая задержка дашбордов, согласованность определений метрик, доступ по ролям, резиденция данных (региональные витрины), стоимость.

## Требования

1. Отдельный **serving-слой (gold)** для BI - быстрые агрегации, не "сырые данные".
2. **Единые определения метрик** (semantic layer / dbt-модели), без дублирующей логики в дашбордах.
3. **Разграничение доступа** (RBAC/RLS) по регионам/тенантам/ролям.
4. **Региональные витрины** + **глобальные агрегаты** только по деидентифицированным данным.
5. Низкая задержка интерактивных дашбордов (p95 запросов в пределах SLA BI).
6. Возможность **самообслуживания** аналитиков (SQL + модели), но с контролем качества (ADR-023).
7. Контроль производительности и стоимости запросов.

## Решение

### Serving-слой: витрины на ClickHouse, моделирование через dbt

- **ClickHouse** - OLAP-serving для BI и real-time аналитики (сохраняется из текущего стека). Хранит только **смоделированные витрины** (gold), а не сырые данные (ADR-019).
- Витрины моделируются **dbt**: `staging` → `marts` (star schema / wide tables), инкрементальные модели; источники - silver Iceberg и потоковые агрегаты Flink.
- **Как silver попадает в ClickHouse**: через **Iceberg table engine** (read-only) в ClickHouse; **dbt материализует витрины как штатные (incremental) таблицы ClickHouse**, а тяжёлые пересборки загружает Spark (детали - ADR-019).
- **Единые метрики**: определения метрик задаются в dbt/семантическом слое, а не в каждом дашборде; это устраняет расхождения отчётов.
- Материализация: near-real-time витрины (из Flink) + периодические batch-витрины (Spark/dbt).

### BI-инструмент: DataLens

- Пользователи работают в **DataLens** поверх витрин ClickHouse; прямой доступ к объектному хранилищу/silver из BI запрещён.
- Подключение - через **read-only сервисный аккаунт** с ограничениями; **row-level security** по `regionId`/`tenantId`.
- Набор дашбордов: бизнес-метрики (поездки, выручка, спрос/предложение), финансы/выплаты, антифрод, операционные метрики, качество данных (DQ-дашборды, ADR-023).

### Глобальный слой

- Региональные витрины - в регионе. **Кросс-региональная** BI-аналитика строится на **глобальном агрегированном слое** (деидентифицированные данные, ADR-014, ADR-024).
- Из регионов в глобальный слой передаются только агрегаты/деидентифицированные данные.

### Самообслуживание

- Аналитики используют dbt + ClickHouse (SQL). Изменения проходят ревью и CI-тесты dbt (ADR-023).
- Тяжёлые ad-hoc запросы изолируются (лимиты, отдельные ресурсные пулы/реплики), чтобы не влиять на критичные дашборды.

## Альтернативы

1. **BI напрямую на lakehouse (Spark SQL).** Больше гибкости для ad-hoc, но выше задержка и сложнее управлять SLA дашбордов.
2. **BI напрямую на операционных БД сервисов.** Создаёт нагрузку на прод и связность доменов с аналитикой, исключено.
3. **Self-service BI нового вендора (Looker/Metabase/Superset).** Дополнительный инструмент и лицензии; текущий DataLens сохраняется.
4. **Только batch-витрины без streaming-агрегатов.** Проще, но нет near-real-time аналитики (surge, hot zones).
5. **Единая глобальная витрина без регионализации.** Нарушает резидентность и добавляет задержку.

## Компромиссы и риски

- **Двойное моделирование** (логика в Flink для стрима и в dbt для batch) рискует расхождением; митигация - единая семантика, сверка агрегатов (ADR-023).
- **RLS/мультитенантность** в ClickHouse усложняет модели и запросы; требуется аккуратная настройка доступа.
- **Региональное дублирование витрин** повышает стоимость хранения/поддержки; компенсируется изоляцией и близостью к пользователям.
- **Ad-hoc запросы** могут конкурировать с дашбордами; митигация - ресурсные пулы и лимиты.
- **Задержка batch-витрин** ограничивает "свежесть" части отчётов; для near-real-time - только те метрики, что идут через Flink.
- **DataLens как единая точка визуализации** - зависимость от вендора; в остальном это существующий стандарт компании.

## Допущения

- DataLens поддерживает подключение к региональным ClickHouse с RLS и сервисными аккаунтами.
- Пропускная способность ClickHouse достаточна для интерактивных дашбордов поверх витрин gold.
- Глобальный агрегированный слой не содержит PII (деидентификация, ADR-024).
