# ADR-021: ML-платформа (обучение, хранение признаков, инференс)

## Контекст

Бизнес-требования описывают три ML-направления:
- **динамическое ценообразование** в реальном времени (NFR-P-04: пересчёт цены p95 ≤ 200 мс);
- **прогнозирование спроса** (для перераспределения водителей и предотвращения "горячих зон");
- **обнаружение мошенничества** (антифрод в критичном пути платежа, риск-скоринг).

Платформа данных (ADR-019) даёт слои bronze/silver/gold и вычислительные движки (Flink/Spark/dbt). Теперь нужно определить **ML-платформу**: где обучать, как переиспользовать признаки между обучением и инференсом, как версионировать и разворачивать модели, как замыкать цикл обратной связи.

Ограничения:
- **Python-команда** (data-инженеры, ML) - решения должны быть посильны ей;
- **cloud-agnostic** и резиденция данных (ADR-013, ADR-014, ADR-017);
- **низкая задержка инференса** для pricing/fraud;
- критичность качества моделей для финансовых решений (Fraud, Pricing).

## Требования

1. **Воспроизводимость обучения**: версионирование кода, данных, окружения, гиперпараметров; повторяемый запуск.
2. **Единое признаковое хранилище** с **offline** (обучение) и **online** (инференс) доступом; отсутствие **training-serving skew**.
3. **Point-in-time correctness** обучающих выборок (без утечки будущего; time travel Iceberg, ADR-019).
4. **Низколатентный онлайн-инференс** (pricing p95 ≤ 200 мс - NFR-P-04; для fraud закрепляется аналогичный бюджет как **производное** требование) и **batch-скоринг** для некритичных задач.
5. **Реестр моделей** с версиями, стадиями и одобрением; управляемый rollout (canary/A-B).
6. **Мониторинг** качества моделей и дрейфа (данных/предсказаний); интеграция с Prometheus/Grafana.
7. **Замкнутый цикл**: предсказания и обратная связь → данные → признаки → переобучение.
8. **Резидентность**: признаки и инференс - в регионе; между регионами - только деидентифицированное и артефакты моделей.
9. **Самообслуживание** data/ML-команд (собственные пайплайны без изменений сервисов).

## Решение

### Компоненты ML-платформы (self-hosted OSS на Kubernetes)

| Компонент | Технология | Роль |
|-----------|-----------|------|
| **Feature Store** | **Feast** | Единые определения признаков (feature repo в Git); offline-store - Iceberg (ADR-019), online-store - Redis |
| **Experiment tracking & Registry** | **MLflow** | Трекинг экспериментов, версии моделей, model registry, стадии (Staging/Production), артефакты в Object Storage. **Единый в hub-регионе** (артефакты/метаданные не содержат PII, ADR-024) |
| **Training** | Python / Spark / GPU-пулы | Обучение моделей (спрос, ценообразование, антифрод), тюнинг, backtests |
| **Orchestration** | Airflow | DAG-и: построение датасетов → обучение → валидация → регистрация → публикация |
| **Model Serving** | **KServe** (KServe/Seldon на K8s) | Онлайн-инференс (автоскейл, canary, A/B), загрузка моделей из MLflow |
| **Batch scoring** | Spark | Периодический пересчёт скорингов/прогнозов для некритичных сценариев |
| **Monitoring** | Prometheus/Grafana + drift-метрики | Дрейф данных/предсказаний, качество модели, SLA инференса |

Компоненты **признаков, обучения и инференса** (Feast, Training-пулы, KServe, Airflow) разворачиваются **per-region** на Kubernetes (cloud-agnostic, ADR-013). **MLflow** (tracking + registry) - **единый в hub-регионе** (ADR-024): его метаданные и артефакты моделей не содержат PII, а обученный артефакт затем реплицируется во все регионы для инференса.

### Feature Store: устранение training-serving skew

- Признаки описываются **один раз** в feature repo (Feast); одни и те же определения используются и для обучения, и для инференса.
- **Offline** (обучение): точки признаков из Iceberg с **point-in-time join** (time travel, ADR-019) - корректно на момент `occurredAt` события.
- **Online** (инференс): материализация (materialization) последних значений в **Redis**; сервис получает признаки за единицы миллисекунд.
- Ключи признаков согласованы с доменом (`driverId`, `zoneId`, `regionId`), что позволяет переиспользовать их в pricing/fraud/booking.

### Обучение и регистрация

- Airflow-пайплайн: `dataset build (Spark)` → `train` → `evaluate/backtest` → `register (MLflow)` → `approve` → `deploy (KServe)`.
- **Версионирование**: MLflow фиксирует git-commit кода, версию датасета (Iceberg snapshot), параметры, метрики, артефакт модели. Любой прод-инференс воспроизводим.
- Модель переводится в **Production** только после проверок качества (ADR-023) и ревью (архитектурный/ML-комитет для критичных - Fraud/Pricing).

### Инференс

- **Онлайн** (KServe): сервисы (Pricing, Fraud, Booking) вызывают модель по REST/gRPC; признаки - из Feast online; результат - в ответе и/или в топик.
- **Batch** (Spark): прогнозы/скоры, не требующие реалтайма (планирование, отчёты), пишутся в gold.
- **Rollout**: canary/A-B через KServe; откат на предыдущую версию при деградации метрик.

### Бюджет задержки онлайн-инференса (NFR-P-04, p95 ≤ 200 мс)

Для Pricing/Fraud инференс находится в критичном пути, поэтому задаётся явный бюджет на вызов (ориентир p95):

| Этап | Бюджет p95 |
|------|-----------|
| Fetch online-признаков (Feast → Redis, co-located) | ≤ 20 мс |
| Вызов модели (KServe, тёплый пул, in-region) | ≤ 50 мс |
| Сетевой хоп сервис ↔ serving (mTLS, in-region) | ≤ 30 мс |
| Прикладная логика/пост-обработка | ≤ 40 мс |
| **Итого (цель)** | **≤ 140 мс** (запас к 200 мс) |

- Достигается **co-location** serving и Redis в регионе, тёплым пулом реплик KServe, предвычислением/кешированием признаков и батчингом.
- Если бюджет не выдерживается (таймаут вызова модели > 180 мс, т.е. с запасом до 200 мс) или модель недоступна - срабатывает **fallback** без деградации критичного пути.

**Fallback-политика (Pricing/Fraud).** При недоступности/таймауте модели сервис использует детерминированное правило (базовый тариф / правила антифрода из БД) либо последнее валидное предсказание из кеша; решение помечается как "без ML" для наблюдаемости. Это гарантирует соблюдение NFR-P-04 и NFR-A-02 (изоляция сбоев) независимо от состояния ML-платформы.

### Обратная связь и мониторинг

- Предсказания логируются (предсказание + признаки + факт) в bronze/gold → становятся обучающими данными следующего цикла.
- **Drift-мониторинг**: сдвиг распределения признаков и предсказаний, деградация метрик → алерт → переобучение.
- Онлайн-цикл переобучения - регулярный (по расписанию/по дрейфу), а не мгновенный.

### Пайплайн доставки моделей (MLOps CI/CD)

Сквозной путь "код → прод" для моделей и данных (согласован с NFR-M-01/02/03 и с schema-CI ADR-007):

1. **CI**: линт/тесты кода и feature-дефиниций; **проверка обратной совместимости схем** (Schema Registry); прогон **dbt-тестов** и DQ-наборов (ADR-023) на тестовых данных.
2. **Обучение по требованию/расписанию**: Airflow-пайплайн в отдельном окружении; артефакт регистрируется в MLflow как **Staging**.
3. **CD/продвижение**: автоматическая валидация (метрики ≥ порога, backtest, проверки bias/дрейфа) → ревью для критичных (Fraud/Pricing) → перевод модели в **Production** в MLflow.
4. **Деплой**: KServe подтягивает Production-версию; раскатка **canary → 100 %**; автоматический откат при деградации SLI инференса.
5. **Данные как код**: dbt-модели, expectation-suites и определения признаков - в Git; изменения проходят тот же ревью-контур (архитектурный комитет для критичного).

CI-запуски изолированы от прод-данных (используют обезличенные фикстуры/выборки), чтобы не нарушать резидентность (ADR-024).

## Альтернативы

1. **Managed ML (DataSphere/Managed MLflow).** Меньше операционной нагрузки, но vendor lock-in, вопросы резиденции и стоимости GPU.
2. **Без feature store (SQL-запросы ad-hoc).** Проще, но высокая вероятность **training-serving skew** и дублирования логики признаков.
3. **In-process инференс (модель внутри сервиса).** Нет сетевого хопа и ниже задержка, но усложняет rollout/откат и версионирование, связывает ML-релиз с релизом сервиса.
4. **Внешний real-time inference-сервис (собственный) вместо KServe.** Больше контроля, но придётся реализовывать автоскейл/canary/A-B самостоятельно.
5. **Обучение централизованно на сырых данных.** Проще, но нарушает резиденцию (ADR-024) - неприемлемо.
6. **Federated learning.** Максимальная приватность, но существенно сложнее; рассматривается как перспектива, не для первой итерации.

## Компромиссы и риски

- **Дополнительная инфраструктура (Feast/MLflow/KServe/Airflow)** - операционная нагрузка и компетенции; митигация - self-hosted на общем K8s, единые практики с платформенной командой.
- **Онлайн-store (Redis) может отставать** от offline (лаг материализации) → риск устаревших признаков; контролируется метрикой свежести признаков.
- **Сетевой хоп к KServe** добавляет задержку в критичный путь pricing/fraud - митигация: co-location в регионе, тёплый пул, батчинг, кеш признаков; контролируется явным **бюджетом задержки** (таблица выше) и fallback-политикой.
- **Стоимость GPU-обучения** и serving; митигация - расписание обучения, спот-инстансы для обучения, автоскейл serving.
- **Дрейф и деградация моделей** - обязательный мониторинг и регламент переобучения, иначе качество падает незаметно.
- **Зависимость критичных решений от ML** (Fraud/Pricing) - нужен **fallback**: бизнес-правила/последнее валидное предсказание при недоступности модели.
- **Governance моделей** - версии, одобрение, аудит решений (ADR-023, ADR-017).

## Допущения

- Kubernetes-кластеры доступны в каждом суб-регионе; GPU-мощности доступны (managed или собственные) для обучения.
- Feast совместим с Iceberg как offline-store и с Redis как online-store в выбранных версиях.
- Единый MLflow (hub-регион) доступен из регионов; артефакт модели реплицируется в регион для инференса (не PII, ADR-024).
- KServe разворачивается в регионах; сетевой доступ сервисов к serving - в пределах региона (низкая задержка).
- Обучение использует деидентифицированные/региональные данные согласно ADR-024.
