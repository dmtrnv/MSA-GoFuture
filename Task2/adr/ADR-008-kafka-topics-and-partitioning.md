## Контекст

Необходимо определить **схему топиков Kafka с партиционированием по регионам**. Целевая нагрузка - 500 тыс. конкурентных поездок, 
при этом платформа расширяется на Юго-Восточную Азию и Южную Америку (NFR-SC-01, NFR-C-01 - резидентность данных).

Нужно одновременно обеспечить:
- **региональную локальность** (данные региона обрабатываются/хранятся в регионе);
- **упорядоченность** событий по ключевым сущностям (поездка, водитель, платёж);
- **горизонтальное масштабирование** потребителей без "горячей" партиции;
- **replay/retention** для восстановления и переобработки.

## Требования

1. Схема топиков по доменам с ролевой моделью (events/commands/retry/dlq).
2. Партиционирование, при котором регион - первичный разрез (ключ `region_id`, 3 региона).
3. Гарантия порядка событий по агрегату в пределах региона.
4. Retention и политики очистки под частоту и назначение топика.
5. Репликация и durability под 99,95–99,99 % (min.insync.replicas, acks=all).
6. Задел под георепликацию.

## Решение

### Регионы

| Регион | Код (`regionId`) | Назначение              |
|--------|------------------|-------------------------|
| Юго-Восточная Азия | `sea` | Целевой рынок экспансии |
| Южная Америка | `sa` | Целевой рынок экспансии |
| Базовый (Россия/СНГ) | `base` | Текущий рынок           |

`regionId` - первый класс домена: входит в конверт события (ADR-007), в ключ партиционирования и в маршрутизацию потребителей.

### Модель топиков

Топики делятся по **домену** и **роли**:

| Роль топика | Суффикс | Назначение |
|-------------|---------|-----------|
| Доменные события | `.<domain>.events.v1` | facts для pub/sub (ADR-007) |
| Команды саги | `.<domain>.commands.v1` | адресные intents (ADR-010) |
| Высокочастотный поток | `.<domain>.location.v1` | `DriverLocationUpdated`, отдельно из-за объёма |
| Retry | `.retry` | повторная доставка с backoff (ADR-011) |
| Dead Letter | `.dlq` | необработанные сообщения (ADR-011) |

### Ключевые топики

> На диаграмме C2 (`diagrams/c2-to-be.puml`) показано только **подмножество ключевых топиков** (без ухода в детали уровня контейнеров): командные топики свёрнуты в один узел `*.commands.v1`, а ряд топиков (например, `geography.zone.events.v1`) на схеме не отображается. **Полный перечень топиков - в таблице ниже**, он является источником истины.

### Партиционирование по регионам

**Первичный разрез - регион.** Для каждого топика партиции разбиваются на **диапазоны по регионам** (region-aware partitioner): например, `0–7` → `base`, `8–15` → `sea`, `16–23` → `sa`. Диапазоны задаются в конфигурации и могут менять размер при росте региона без изменения ключей.

**Ключ сообщения - составной:** `regionId:aggregateId` (например, `sea:booking-00123`).

- Регион гарантирует **локальность** и возможность регионального консьюминга (резидентность NFR-C-01).
- `aggregateId` внутри региона гарантирует **порядок** событий по конкретной поездке/водителю/платежу.
- Композитный ключ даёт **внутрирегиональную параллельность** (в отличие от ключа "только regionId", который загнал бы весь регион в одну партицию и одну "горячую" точку).

Для `driver.driver.location.v1` ключ - `regionId:driverId`: события каждого водителя упорядочены, а 48 партиций дают масштаб по числу водителей.

### Durability и репликация

- **replication.factor = 3**, **min.insync.replicas = 2** (для критичных финансовых топиков - 3), `acks=all`.
- Продюсеры **идемпотентны** (`enable.idempotence=true`); для финансовых доменов - транзакционный продюсер (exactly-once на границе БД-топик, ADR-011).
- **replay** обеспечивается retention + возможностью сброса consumer offset (retention ≥ 7 дней для доменных событий).
- **Компакция (log compaction):** для "снимков состояния" (например, `driver.driver.state`), чтобы новый потребитель получал последнее состояние сущности.
- **Георепликация** между региональными кластерами - детальная прорабокта в будущем; здесь закладываем топики и ключи так, чтобы региональную реплику можно было вести без перестроения схемы.

### Соглашения

- Имена топиков: строчные, разделитель `.`, `<domain>.<entity>.<role>.v<major>`.
- Партиций всегда ≥ числа потребителей целевого consumer group для линейного масштабирования.
- Создание топиков - как код, с ревью архитектурного комитета; автосоздание топиков **выключено**.

## Альтернативы

1. **Один топик на весь регион.** Меньше топиков, но нет разделения по доменам и ролям, разный retention и шаблоны доступа.
2. **Ключ = только `regionId`.** Просто, но высокая концентрация в одной партиции и потеря порядка по сущности при масштабировании.
3. **Ключ = только `aggregateId` (без региона).** Хороший порядок по сущности, но теряется региональная локальность и усложняется резидентность.
4. **Topic-per-region (`booking.events.sea`, `…sa`, `…base`).** Явное разделение, но разрастание числа топиков и дублирование ACL; выбран region-aware partitioner в одном топике как более управляемый вариант. В будущем при необходимости можно перейти к topic-per-region.
5. **Auto-create топиков.** Быстро, но неконтролируемо (неверные партиции/retention).

## Компромиссы и риски

- **Композитный ключ** усложняет объяснение, но даёт и локальность, и порядок, и параллельность.
- **Диапазоны партиций по регионам** требуют перебалансировки при неравномерном росте регионов - решается на этапе регламентной операции.
- **48 партиций на location-топик** × топики × регионы - операционная и cost-нагрузка (FinOps, NFR-COST-02); уточняется по факту пропускной способности.
- **Retention 24 часа для location** ограничивает окно replay для гео-событий; для аналитики они параллельно пишутся в ClickHouse.
- **Резидентность:** до появления региональных кластеров данные физически в одном кластере - требуется временная компенсация/план до геораспределения.

## Допущения

- Yandex Managed Kafka покрывает требуемое число партиций и пропускную способность в каждом регионе.
- Формат сериализации - **Avro** (ADR-007); схема ключа неизменна в рамках major-версии топика.
