## Контекст

В ADR-006 принято решение о едином event-driven backbone на Apache Kafka и надёжной публикации через **Transactional Outbox**. 
Сейчас требуется спроектировать **доменную модель событий**.

Чтобы события были контрактом между автономными сервисами (а не внутренним форматом одного сервиса), нужна единая договорённость о:
- классификации и именовании событий;
- структуре стандартных полей сообщения (envelope) и полезной нагрузки (payload);
- версионировании схем и совместимости (без нарушения контрактов - NFR-COMPAT-02);
- различие типов сообщений (доменное событие, команда, служебное).

## Требования

1. Единый каталог доменных событий по всем доменам (Booking, Driver, Pricing, Payments, Payouts, Notification, Geography, Analytics, Fraud).
2. Единый **event envelope** для трассировки, идемпотентности, региональности и мультитенантности.
3. **Fact-based** события: событие описывает случившееся в прошлом факте, в терминах домена, без утечки внутренних деталей реализации.
4. Разделение **событий (facts)** и **команд (intents)**.
5. Версионирование и обработка эволюции схем без breaking changes.

## Решение

### Типы сообщений

| Тип                        | Назначение | Пример |
|----------------------------|-----------|--------|
| **Доменное событие (fact)** | Уведомление: "что уже произошло" | `BookingCreated` |
| **Команда (intent)**       | Адресное указание: "сделай это" | `PaymentAuthorizeRequested` |
| **Служебное**       | Ретраи, DLQ, снимки состояния | `retry`, `dlq` |

### Соглашения именования

- **Тип события:** `PascalCase`, `<Сущность><Действие в прошедшем времени>`: `BookingCreated`, `DriverLocationUpdated`, `PaymentCaptured`, `TripCompleted`.
- **Топик:** `<domain>.<entity>.<kind>.v<major>`: `booking.booking.events.v1`, `driver.driver.location.v1`. Полное описание - ADR-008.
- **Ключ раздела (partition key):** `regionId:<aggregateId>` (см. ADR-008).
- **Владелец события-факта - ровно один домен** (его продюсер): факт живёт в топике своего домена, потребители владение не переносят.

### Каталог доменных событий (ключевые)

| Домен | События (facts) | Команды (intents) | Частота |
|-------|----------------|-------------------|---------|
| Booking | `BookingRequested`, `BookingCreated`, `BookingConfirmed`, `TripStarted`, `TripCompleted`, `BookingCancelled`, `TripCancelled` | `BookingCancelRequested` | высокая |
| Driver | `DriverRegistered`, `DriverStatusChanged`, `DriverLocationUpdated`, `DriverAssigned`, `ShiftStarted`, `ShiftEnded` | `DriverAssignmentRequested`, `DriverReleased` | **очень высокая** |
| Pricing | `PriceQuoted`, `SurgeMultiplierUpdated`, `FareCalculated` | `PriceQuoteRequested` | высокая |
| Payments | `PaymentAuthorized`, `PaymentCaptured`, `PaymentFailed`, `PaymentRefunded` | `PaymentAuthorizeRequested`, `PaymentCaptureRequested`, `PaymentRefundRequested` | средняя |
| Payouts | `PayoutInitiated`, `PayoutCompleted`, `PayoutFailed` | `PayoutRequested` | средняя |
| Notification | - | `NotificationRequested` | высокая |
| Geography | `ZoneUpdated`, `GeoIndexUpdated`, `RouteCalculated` | `RouteCalculateRequested` | высокая |
| Fraud | `FraudDetected`, `RiskScored` | `FraudCheckRequested` | высокая |
| Analytics | - | - | - |

Команды в каталоге отнесены к домену-**получателю** (кто их обрабатывает), а не к домену-отправителю. Например, `DriverAssignmentRequested`/`DriverReleased` исполняет Driver, хотя инициирует их Saga Orchestrator (компонент Booking, ADR-010).

### Event envelope (обязателен для всех сообщений)

```json
{
  "eventId": "b1f2c3d4-...",          // UUID, ключ идемпотентности
  "eventType": "BookingCreated",       // логическое имя типа сообщения (факт/команда), без версии
  "eventVersion": 1,                    // major-версия контракта (совпадает с v<major> в топике; не версия схемы в реестре)
  "occurredAt": "2026-10-14T10:15:30Z", // время факта (event-time)
  "publishedAt": "2026-10-14T10:15:30Z",// время публикации (для publish-lag)
  "regionId": "sea",                    // регион (NFR-C-01), ключ партиционирования
  "tenantId": "partner-acme",           // мультитенантность, nullable
  "aggregateType": "Booking",
  "aggregateId": "booking-00123",
  "sagaId": "saga-7f3a...",             // сага-контекст (ADR-010), nullable вне саги
  "correlationId": "req-...",           // сквозная трассировка (NFR-O-02)
  "causationId": "evt-...",             // событие-причина
  "producer": "svc-booking",
  "payload": { "...": "..." }           // только необходимые для контракта поля
}
```

Правила:
- **Payload минимален** - только данные, нужные потребителям; "толстые" объекты не передаём (падение пропускной способности).
- **PII** не попадает в события без необходимости; для чувствительных данных - только ссылки/ids, детали потребитель дозапрашивает (комплаенс, NFR-C-01).
- Все потребители **идемпотентны** по `eventId` (ADR-011).
- **`sagaId`** заполняется для команд и событий-результатов, участвующих в саге (ADR-010), и связывает их в один процесс; вне саги - `null`. Ключ идемпотентности шага саги - пара `sagaId` + шаг (`eventType`).
- **`schemaId`/`schemaUri` в envelope отсутствуют.** Числовой `schema ID` не является бизнес-полем конверта - это часть Avro wire-format заголовка (см. ниже). Схему (writer schema) однозначно задаёт именно `schema ID` из wire-format; а `eventType` + `eventVersion` идентифицируют **логический контракт** (тип сообщения и его major-версию), а не запись в реестре. Дублировать ссылку на схему внутри payload нельзя.
- Терминология: `eventVersion` - **major-версия публичного контракта**, совпадающая с `v<major>` в топике; она **не** равна версии subject в реестре и не меняется при обратно-совместимых правках. Текущая версия схемы в реестре выражается subject-version / `schema ID`.

### Формат сериализации

- Формат схем - **Avro**: компактность, schema resolution, нативная поддержка реестра. JSON - только для низкочастотных служебных топиков.
- Сообщение в Kafka - Avro **wire-format**: `magic byte (0x0)` + `4-byte schema ID` + Avro-payload. Сама схема в брокер не пишется - в сообщении только `schema ID`.
- **`schema ID` - транспортный, а не бизнес-уровень:** сериализатор добавляет его в префикс Kafka-key и Kafka-value автоматически, **вне** Avro-payload. В envelope (`eventId`, `eventType`, …) его нет - продюсер не управляет им как полем контракта.

### Жизненный цикл схем (как схемы попадают в реестр)

- **Schema Registry** - единый источник истины контрактов; хранит схемы per-**subject**.
- **Subject naming:** `<topic>-value` (payload) и `<topic>-key` (ключ), например `booking.booking.events.v1-value`. Соответствует модели топиков (ADR-008).
- **Регистрация при публикации (продюсеры):** продюсер (outbox-relay сервиса, Flink) при первой отправке в топик вызывает serializer, который делает `POST /subjects/{subject}/versions`. Реестр сравнивает схему с предыдущими версиями subject по режиму совместимости и возвращает **`schema ID`**; при несовместимости - ошибка, публикация не проходит.
- **Чтение (потребители):** потребитель достаёт `schema ID` из сообщения и запрашивает `GET /schemas/ids/{id}`, резолвит writer/reader-схемы и **кеширует** их локально. Реестр не находится в горячем пути обработки каждого сообщения.
- **Governance:** схемы - как код в репозиториях сервисов; изменения ревьюит архитектурный комитет; в CI (Jenkins) выполняется проверка обратной совместимости перед деплоем. Регистрация схем вне процесса не допускается.
- **HA/отказоустойчивость:** реестр разворачивается в HA (несколько инстансов master/slave, состояние - в служебном compacted-топике `_schemas` кластера Kafka). При кратковременной недоступности клиенты продолжают работу за счёт локального кеша схем.

### Версионирование и совместимость

- Режим совместимости - **BACKWARD** (допускается `FULL_TRANSITIVE`).
- Major-версия входит только в имя **топика** (`...v<major>`) и дублируется полем `eventVersion`; `eventType` - логическое имя типа без версии (`BookingCreated`). Обратно-совместимые изменения (добавление опционального поля с default) `eventVersion`/имя топика **не меняют** - растёт только версия subject в реестре.
- Breaking change ⇒ новый major-топик (`...v2`) и период двойной публикации v1+v2 (см. ADR-011).
- Эволюция только аддитивная; удаление/переименование полей запрещено.

## Альтернативы

1. **Схемы без реестра (JSON-free).** Гибко, но нет контроля совместимости и контрактов, нарушает NFR-COMPAT-02.
2. **Только команды (command-driven).** Централизует оркестрацию, но снижает автономность и реактивность доменов.

## Компромиссы и риски

- **Envelope добавляет накладные расходы** на каждое сообщение; критично для `driver.location` (десятки тысяч сообщений/с). Митигация: компактный конверт, бинарный формат (**Avro**) для горячих топиков, раздельные топики по частоте.
- **Schema Registry становится критичным узлом** - разворачивается self-hosted в HA, клиенты кешируют схемы и переживают кратковременную недоступность (см. "Жизненный цикл схем").
- **PII/комплаенс:** события могут реплицироваться между регионами; требуется контроль, какие поля допустимо пересекать (NFR-C-01).
- **Совместимость:** строгий BACKWARD-режим может замедлять эволюцию; компенсируется регламентом ревью схем (архитектурный комитет).

## Допущения
