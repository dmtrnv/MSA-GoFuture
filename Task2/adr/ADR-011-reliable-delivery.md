## Контекст

Event-driven платформа на at-least-once доставке (NFR-A-06) работает при 500 тыс. конкурентных поездок и обязана **не терять события** 
и **не порождать фантомные эффекты**. Необходимо реализовать механизмы обеспечения надёжной доставки. 

Есть два класса рисков:

1. **Потеря/дубликаты на стороне продюсера** - сервис записал данные, но событие не ушло (или наоборот), классическая проблема dual-write БД+брокер.
2. **Сбои на стороне потребителя** - падение в середине обработки, "отравленные" (poison) сообщения, зависшие ретраи, нарушение порядка.

## Требования

1. Атомарность "запись данных + публикация события" (без потери и фантомов).
2. Гарантия доставки at-least-once + идемпотентное потребление (NFR-A-06).
3. Ретраи с backoff, dead-letter topic, разбор "отравленных" сообщений.
4. Сохранение порядка событий по агрегату (ADR-008).
5. Replay для восстановления потребителей.
6. Exactly-once там, где критично (финансы).
7. Совместимая эволюция схем при изменениях.

## Решение

### 1. Надёжная публикация - Transactional Outbox

Сервис в **одной транзакции** с бизнес-данными пишет событие в таблицу `outbox` этого же сервиса:

- Отдельный **relay** (polling publisher внутри сервиса, `SELECT ... FOR UPDATE SKIP LOCKED`) читает outbox и публикует в Kafka идемпотентным продюсером, затем помечает запись отправленной.
- Публикация возможна **минимум один раз** (at-least-once) - при сбое между публикацией и пометкой возможен дубликат; это допустимо, потребители идемпотентны.
- Метрика **`outbox_publish_lag`** и размер необработанного outbox - ключевые SLI (ADR-012).
- Партиционирование outbox-таблицы по дате + очистка после отправки (контроль роста).

### 2. Идемпотентное потребление

- Каждый потребитель хранит обработанные `eventId` в **dedup-хранилище** (таблица `processed_events(event_id, consumer, processed_at)` в БД сервиса, либо Redis с TTL).
- Обработка события + запись в `processed_events` - **в одной транзакции** (локальная идемпотентность).
- Операции проекций - **upsert** (по `aggregateId`), а не append, чтобы повтор не создавал дубликаты.
- Ключ идемпотентности для команд/саг - `sagaId` (ADR-010).

### 3. Ретраи и Dead Letter

- Потребитель при транзиентной ошибке (таймаут внешнего API, БД недоступна) - отвечает повторной обработкой через **retry-топик** с **экспоненциальным backoff** (`*.retry`), не блокируя партицию. Реализация без потери порядка: ретрай-топик партиционируется тем же ключом, что и исходный (порядок по агрегату сохраняется).
- После N попыток (например, 5) или при **non-retryable** ошибке (валидация, схема) - сообщение уходит в **`*.dlq`**.
- **DLQ** разбирается: алерт + ручная/полуавтоматическая переобработка (replay из DLQ после исправления). Метрика `dlq_size` - на дашборд и в SLO.
- **Poison pill** не блокирует поток: изоляция в DLQ + алерт.

### 4. Порядок, offset и replay

- Порядок гарантируется **внутри партиции** (ключ `regionId:aggregateId`, ADR-008) - ретраи идемпотентны и не "переставляют" события агрегата.
- Offset коммитится **после** успешной обработки + завершения транзакции (at-least-once).
- **Replay:** сброс offset consumer group на нужное время; retention топиков (ADR-008) определяет окно. `driver.location` имеет короткий retention (24 ч) - для аналитики дублируется в ClickHouse.

### 5. Exactly-once и финансы

- Для финансовых доменов (Payments, Payouts) применяется **транзакционный продюсер** (Kafka EOS) на границе "БД-топик": писатель outbox может публиковать в рамках Kafka-транзакции с отправкой offset'ов - снижает окно дубликатов.
- Полная сквозная exactly-once невозможна (внешний банк API, UI) - там **идемпотентные операции + ключи дедупликации** на стороне внешнего провайдера.
- Компенсации саги (ADR-010) семантически идемпотентны.

### 6. Совместимость схем

- Все схемы - через **Schema Registry**, формат **Avro**, режим **BACKWARD** (ADR-007).
- **Регистрация:** продюсер (outbox-relay, Flink) при первой публикации регистрирует схему в subject `<topic>-value` (`POST /subjects/{subject}/versions`) и получает `schema ID`, который пишется в Avro wire-format. Несовместимая схема отклоняется реестром - публикация не проходит.
- **Чтение:** потребители резолвят схему по `schema ID` (`GET /schemas/ids/{id}`) и кешируют её; реестр не в горячем пути.
- **Governance:** схемы - как код; изменения ревьюит архитектурный комитет, CI проверяет обратную совместимость перед деплоем.
- Breaking change - новый major-топик и окно двойной публикации v1+v2; потребители мигрируют по контрактным тестам (ADR-004).

### 7. Ограничение времени и защита от зависаний

- Таймауты обработки; "зависшие" сообщения определяются по метрике обработки и попадают в DLQ по истечении времени.
- Circuit breaker/backpressure на внешних вызовах (NFR-A-02), чтобы медленный внешний сервис не забивал партицию.

## Альтернативы

1. **Dual-write (БД + Kafka двумя вызовами).** Не атомарен - потеря/фантомы при сбое между записями.
2. **CDC (Debezium) как источник публикации вместо Outbox.** Надёжно, но добавляет коннектор и завязку на схему БД; допустимо для read-моделей, но как основной канал - сложнее контролировать доменные события.
3. **At-most-once.** Проще, но допускает потерю событий - противоречит NFR-A-06.
4. **Бесконечные ретраи без DLQ.** Риск вечной блокировки партиции "отравленным" сообщением.
5. **In-memory дедупликация.** Теряется при рестарте.

## Компромиссы и риски

- **Outbox добавляет запись** в каждую транзакцию и асинхронный лаг публикации; критично для горячих сервисов - компактный конверт, партиционирование outbox, метрика лага.
- **Dedup-хранилище** растёт; очистка по TTL/retention и окну replay (хранить не дольше, чем возможно переигрывание).
- **Retry с backoff** повышает итоговую латентность событий; не влияет на синхронный критичный путь (остаётся REST/gRPC).
- **DLQ требует регламента разбора** - без него превращается в свалку; алерты и runbook обязательны.
- **Exactly-once только на границе БД-топик**; сквозную гарантию даёт комбинация идемпотентности и компенсаций.
- **Порядок при ретраях** сохраняется ценой пропускной способности партиции (задержка последующих событий того же агрегата); для location-потока порядок по водителю приемлем.

## Допущения

- Каждый сервис имеет собственную БД (database-per-service, ADR-002) - outbox и dedup локальны для сервиса.
