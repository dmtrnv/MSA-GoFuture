## Контекст

Нужно выбрать, где заканчивается "обычный consumer" и где нужен специализированный потоковый движок, и обосновать выбор под реальные 
задачи (динамическое ценообразование в реальном времени, умное перераспределение водителей).

Ключевые нагрузки:
- `DriverLocationUpdated` - сверхвысокая частота (гео-события по 500 тыс. поездок);
- **surge-ценообразование** - оконная агрегация спроса/предложения по зонам в реальном времени;
- **hot zones / перераспределение** - поиск скоплений водителей по окнам;
- трекинг поездки, сессии пассажира/водителя.

## Требования

1. Простые сценарии "событие → действие" без лишней инфраструктуры.
2. Stateful/windowed обработка (event-time, watermarks, окна, state store) для цен и гео.
3. Масштабирование по партициям, at-least-once (NFR-A-06), идемпотентность.
4. Реализуемость силами **Python-команды**.
5. Соответствие существующему стеку (в компании уже применяются Spark/Flink).

## Решение

### Двухуровневая модель обработки

1. **Обычные Kafka-консьюмеры внутри доменных сервисов** (Python, тот же код-база/деплой, что и сервис):
   - простые stateless-сценарии: Notification на `BookingCreated`, Payouts на `TripCompleted`, Analytics-ingest в ClickHouse, Fraud-скоринг транзакций, проекции read-моделей;
   - реализуются как listener/loop с ручным commit offset, `acks`-семантикой и идемпотентной обработкой (ADR-011).
2. **Flink (Apache Flink, Python API)** - единый движок для **stateful/windowed** задач:
   - job `surge-pricing`: оконная (tumbling/sliding) агрегация спроса (запросы поездок) и предложения (онлайн-водители) по геозонам → публикация `SurgeMultiplierUpdated`;
   - job `hot-zone`: кластеризация `DriverLocationUpdated` по окнам → сигналы перераспределения;
   - job `trip-session`: сессии поездки из потока событий Booking/Driver.
   - Топология: source-топики → keyBy(zone/regionId) → window → state → sink-топик (Kafka). Event-time + watermarks для корректности при задержках гео-событий.

### Почему Flink

Flink уже используется в компании и предлагает из коробки state, event-time и watermarks.

### Почему не только консьюмеры

Для оконных агрегаций по 48 партициям с обработкой событий не по порядку прибытия обычные консьюмеры потребовали бы вручную реализовывать state store, watermarks, чекпоинты и перебалансировку. Это дублирование того, что даёт Flink "из коробки", и источник ошибок в критичном ценообразовании.

## Альтернативы

1. **Kafka Streams (JVM-сервис).** Нет поддержки Python-версии; лишний язык в Python-организации.
2. **Только обычные консьюмеры, всё руками.** Минимум инфраструктуры, но state/windowing/event-time реализуются вручную - высокий риск в критичном пути, дороже поддержка.
3. **Лёгкие Python-библиотеки (Quix Streams / Faust).** Без JVM и отдельного кластера, ближе к обычному сервису; но слабее по state-гарантиям и event-time на нагрузке 500k - можно рассмотреть как упрощённую замену Flink, если эксплуатация Flink окажется дорогой.
4. **Только Flink для всего.** Единый движок, но простые сценарии удобнее в сервисах (транзакции с БД, доменные правила).

## Компромиссы и риски

- **Два способа обработки** (консьюмеры + Flink) усложняют регламент: нужна граница "что где" (stateless → сервис, stateful/windowed → Flink).
- **Flink - отдельная инфраструктура** (JobManager/TaskManager, чекпоинты, savepoints): операционная нагрузка и стоимость. Митигация: managed-сервис, единый движок на все stateful-джобы.
- **Видимость под вопросом:** топология решений смещается из сервисов в Flink → нужна наблюдаемость джобов (см. ADR-012).
- **Холодный старт и восстановление** job'ов из savepoint/чекпоинта при сбое - регламент обновления.
- **Задержка watermarks:** гео-события могут быть out-of-order; окно/допуск допустимой задержки настраивается per-region.

## Допущения

- Yandex Managed Flink (или self-hosted с S3-совместимым хранилищем) доступен; Flink-версия совместима.
- Ключи партиционирования (ADR-008) обеспечивают корректный keyBy по геозоне/региону.
